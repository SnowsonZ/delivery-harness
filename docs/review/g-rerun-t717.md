## 结论

**R2 合同制路径走通了**：同一个 PR、同一条链上依次有 CI 通过 → 可信评审标记（新口径，通过、0 发现）→ 设计方复核标记 → harness 重跑 → route 判定自动合并 → 批准 App 批准并绑定合并 head → 同步 App 的原生自动合并 → 合并；复核后落后并被同步，同步后的新 head 上两个标记仍被认可；合并账本 `harness-audit/2026/181.json` 里有评审阶段（head ee3ae03、结论通过、评审方 codex、评论 6031227405），同步后评审证据仍在。账本里的 `head_mismatch` 只对应第一轮评审（5329756，不通过）：补提交改了测试，内容不同，账本不沿用它，是对的。

**与 G 原判据的偏离**：制造「落后」的文档 PR（#182）在复核**之前**合并，而不是之后；原因是复核一发布，harness 重跑加判定约 4 分钟就会自动合并，而文档 PR 自己走完 CI 与自动合并也要约 4 分钟，来不及在窗口里完成。偏离后的做法让评审标记和复核标记**都**在旧 head 上发布，再经同步到新 head，检验强度不低于原判据。

**没有走通的观测面（待办 B116）**：
- `bin/harness trace 181`（按 PR 号）与 `trace --ci T717` 都失败：`gh pr view --json baseRepository` 在 gh 里不是合法字段（`engine/core/events_io.py:649`、`engine/reports/ledger.py:107`），自 T305 起如此，单元测试的桩替它返回了这个字段所以一直没被发现。`trace T717` 只能看到本机窗口的 185 个事件，摘要已贴进 #181。
- 所有合并账本（#171 至 #182）的 `missing` 里都有 `ci_events: api` 与 `route: not_found`，`class`、`risk` 为空。
- `bin/harness audit 181` 退出码 1，4 项错误：`ledger_mismatch` ×2、`missing_route`、`reference_unavailable`（CI 事件包不可用）。对照 #182（无同步）与 #178（人工合并）有同样的错误，**是既有问题，不是 T717 或同步造成的**。引用核对 107 项中通过 105、不符 0。

**判定**：G「有保留通过」——合并链路本身走通，观测面（trace、账本、审计的 CI 部分）因 B116 不可用，需要先修 B116，B46 的 G3（真实派发 PR 全链核对）才有意义。
