## 结论

这份设计把调研报告落成 Agent-Notification 的目标态交付系统：**每类任务开工前有机器判定，完工后由 Agent 之外的机器重跑并留证据；自治度按“任务类别 × 风险”由数据放开、超预算自动收紧；人只定义意图、维护 harness、处理例外。**

- **现状：门禁强、数据弱、隔离缺。** 验证与集成两环已是机器闭环（修复证据、base 测试、41 个回放、变异、R0 自动合并），但执行方共用主目录，没有运行轨迹和停机开关，也没有任何 pass^k 数据——能力建在了数据前面（第二节）。
- **主线一：合同与准入。** 任务书改为由你审的合同（R2），验收必须挂规格编号，派发前由 `taskbook.py` 准入；执行方对合同只读（第四节）。
- **主线二：确定性派发。** `bin/dispatch` 在固定槽位 worktree 中运行执行方，负责认领、信任预检、预算与卡死检测、开 PR 和运行记录；执行方只做“实现”和“按报错修复”（第六、七节）。
- **主线三：数据驱动的放权。** `policy.py` + `autonomy.toml` 按停机开关、风险、类别、误差预算、规模决定是否自动合并；升级由你改策略表并附周报证据，降级由脚本即时生效；独立评审与评测集（留出判定、pass^3）提供放权证据（第八、九、十四、十五节）。
- **保留与裁剪。** 保留 verify、修复证据、base 测试、回放、变异、三层护栏、在 main 上执行的 auto-merge。不上合并队列、OpenTelemetry、金丝雀，分别以严格检查、对齐语义约定的运行记录、“自用先行 + 重发上一版”代替（附录 A.2）。
- **路线。** 三阶段约 7–9 周，目标 M2：K1、K2 在 L4 且有数据，K3 按规则完成一次升级或明确不升。L5 不在本期，前置条件是单独系统用户、停机演练与注入回放全拦（第十六节）。
- **需要你拍板。** 第十七节共 9 项，前四项已于 2026-09-28 决定：任务书按类别审、R0/R1 保持自动合并但加强 R1 判定并抽审、必过检查改严格、开启密钥扫描。

阅读顺序：结论 → 第三节总览图 → 第十五节放权规则 → 第十六节路线 → 第十七节决定；各环节细节在第四至十四节，每节末尾是机器验收。

## 一、设计依据与约束

本设计把调研报告《低人工干预下 AI Agent 持续高质量交付：理论与全链路最佳实践》（下称“报告”）落到 Agent-Notification。范围是交付系统本身（harness、流程、角色），不涉及产品功能。

目标态一句话：**每一类任务开工前有机器可执行的完成判定，完工后由 Agent 之外的机器重跑并留下证据；自治度按“任务类别 × 风险”用数据逐级放开，超出误差预算自动收紧；人只定义意图、维护 harness、处理例外。**（报告“核心结论”、第三节）

### 1.1 报告八条原则在本设计中的硬约束

| 报告原则（3.2） | 本设计的硬约束 | 主要落点 |
| --- | --- | --- |
| 先有判定器，再放权 | 任一任务类别升到 L4 之前，必须同时具备该类的判定器清单、误差预算与抽审记录；有运行时影响的类别（K2 起）还须有评测集上的 pass^k | 八、十四、十五 |
| 确定性优先 | 派发、推送、开 PR、风险与类别判定、预算计数、周报、降级全部由脚本完成；模型只做“实现”“按报错修复”“评审”三类节点 | 六、九、十四 |
| 生成与验证分离 | R2 及以上的任务，执行方、评审方、任务设计方三者分离；判定用 main 上的 harness 在 CI 重跑；评审不看执行方轨迹 | 八、十三 |
| 结构防护胜过提示词 | 新规则一律以守卫、CI 检查、ruleset 或 workflow 条件落地；AGENTS.md 与提示词只做说明，不承担拦截 | 七、八、十二 |
| 小批量、可回滚 | 一个任务一个 PR；超过规模阈值不自动合并；发版可重发上一版 | 九 |
| 状态外置、上下文从简 | 任务书是合同，运行记录与台账在仓库或 GitHub；执行环境随时可丢弃 | 四、六、七 |
| 自治度按类别 × 风险，数据驱动 | 策略表 `harness/autonomy.toml`：升级由用户改表（R3），降级由脚本按误差预算即时生效 | 十五 |
| 每次失败沉淀为 harness 改进 | 每个逃逸缺陷必须变成回放或守卫测试并进入评测集；每周做错误分析 | 十一 |

### 1.2 必须继承的既定决定

以下是用户已做的决定（[可验证交付方案](https://github.com/SnowsonZ/Agent-Notification/blob/main/docs/plans/verifiable-delivery.md) §3、§4、§8、§10），本设计不推翻：

- 自治目标 L4：R0/R1 门禁全绿自动合并，R2 以上由用户审证据包后合并（2026-09-25）。
- 角色：Codex、Claude Code 做设计与评审；Zcode、OpenCode、Pi 做执行；用户定意图、审批 R2 以上、确认版本号与发版、做真机验收。
- Agent 不合并、不批准 PR（D4）；Agent 用单独账号 Snowson，R0/R1 由专用 GitHub App 批准，凭据只在允许 main 的 environment 中（D3）。
- 不上 Temporal、OpenTelemetry、合并队列、金丝雀发布（§8）。本设计遵守这一条，用轻量等价物替代：运行记录的字段对齐 OpenTelemetry 的 GenAI 语义约定但不引入其基础设施；用严格必过检查代替合并队列；用“自用先行 + 可重发上一版”代替金丝雀与自动回滚。每处裁剪的理由见附录 A。

### 1.3 方法

- 每个环节回答报告第三节的三个问题：行动前用什么约束（引导），行动后用什么检查（传感），失败时怎么升级。
- 每个组件标注 **保留 / 改造 / 新增**。新增组件写明它编码的假设和删除条件：报告 7.5 指出，harness 的每个组件都编码了“模型自己做不到什么”的假设，这些假设要反复检验。
- 能写成计算型检查的，不写成推理型检查；能写成检查的，不写成文字规则（报告 2.2、11.3）。
- 文中的数字门槛（预算、阈值、窗口）都是初值，按报告 11.5 每季度或每次换执行方模型后复核。
- 报告面向大团队的做法按单人项目裁剪，裁剪处写明理由；仓库路径以 `origin/main` 的 fa1571e（PR #47）为准。

### 2.2 成熟度判断

对照报告 16.2 的五级成熟度：

- **M1（受监督执行）** 的能力大部分具备（统一 verify、AGENTS.md、R2 以上人审），唯独“在沙箱中完成任务”不满足：执行方与评审方都在主工作目录运行，2026-09-27 已经发生两个 Agent 抢同一目录的冲突（G1）。
- **M2（门禁自治）** 的门禁能力已提前建好（分层门禁、防篡改、R0 自动合并、升级包），但 M1 进入 M2 的准入数据一项都没有：没有 20–50 个任务组成的回归评测集，没有 pass^k，没有可信的无修改合并率（自动合并的 PR“无需修改”是流程造成的）。
- **结论：能力建在了数据前面。** R0 没有运行时影响，自动合并可以保留；R1 至今一次都没自动合并过，判定只靠提交里自报的 `Risk: R1`、路径和已有测试是否改动，证明不了行为不变，应加强机器判定并抽审（C1；2026-09-28 决定不收回自动合并）。本设计的主线是补上数据与隔离，让已建的自治有证据支撑，而不是再加门禁。

### 3.2 五个关键设计决定

1. **合并策略是数据，判定在 main 上执行。** 策略写在 `harness/autonomy.toml`，由 `auto-merge.yml` 用 main 上的代码读取（沿用现有 `workflow_run` 做法），PR 改不了自己的待遇。
2. **升级人定，降级自动。** 降级信号（逃逸登记、停机开关、预算超限）谁都能触发，只会让系统更保守；升级只能改策略表（R3，用户批准）并附周报证据（报告 2.6 误差预算、10.3）。
3. **确定性编排包住智能体节点。** 派发、推送、开 PR、等 CI、计轮次都由脚本完成，执行方只在“实现”和“按报错修复”两个节点工作（报告 6.4：Stripe 的 blueprint、Airbnb 的状态机）。
4. **固定槽位，而不是每个任务新建目录。** Zcode、Pi、Codex 的项目钩子信任按路径记录，未信任时守卫静默失效。固定槽位让用户每个槽位只授权一次，Agent 既不需要也不能代为授权。
5. **运行记录只存结构化摘要。** 不存对话正文、输入内容或凭据（AGENTS.md 的隐私约束）；完整轨迹留在本机被忽略的 `build/runs/`。

## 四、环节 1：需求与规格——让“完成”可被机器判定

报告依据：4.1–4.5；3.1（意图与验收是人杠杆最高的投入）；16.1（准入按“可验证性 × 风险”分诊）。

|  | 设计 |
| --- | --- |
| 引导 | 任务书合同：终态、非目标、前置条件、挂规格编号的验收表、步骤、预算 |
| 传感 | `taskbook.py` 准入检查；`acceptance.py` 编号 ↔ 测试映射；执行方主动澄清 |
| 升级 | 准入不过即拒绝派发；验收无法判定时执行方提交“澄清”升级包 |

### 4.1 任务书即合同（改造，C3）

- **按任务类别决定是否需要用户审（2026-09-28 决定）**：`docs/templates/**`、`docs/plans/task-*.md`、`docs/plans/backlog.md` 的风险按任务类别判定：护栏与流程类（K7）和架构级变更（跨两个以上模块、新增或修改公共接口如 CLI 输出与数据格式、数据迁移、新增依赖）的任务书需用户审；业务修改、缺陷修复的任务书通过准入检查即自动合并；模板与待办清单仍需用户审。类别写低不影响安全：实现 PR 仍按实际改动路径判定风险，业务改动的实现 PR 为 R2，用户审实现时一并看到任务书。历史调研、评审、说明仍为 R0；`docs/plans/` 下其余方案文档仍为 R0，其中若写了验收或决定，应迁入规格或任务书。
- **执行方只读**：守卫对 implementer 角色拒绝编辑 `docs/plans/task-*.md` 与 `docs/specs/**`。合同是判定器的一部分，与“执行方不能改判定器”同理（报告 2.5）；需要改合同时，执行方写升级包。
- **机器可读头部**：任务书开头加一段 YAML front matter，供准入检查、派发与度量读取：

```yaml
task: T005
class: K2              # 任务类别，见第十五节
risk: R0               # 预期风险；CI 仍按路径独立判定，不一致时取高者
designer: claude-code  # 任务设计方，用于评审分离
spec_refs: [DR14]      # 挂钩的规格验收编号；不挂时写 no_spec_reason
budget:
  wall_clock_min: 60
  ci_rounds: 3
  retries: 2
  tokens: null         # 宿主能报时填写
rollback: git revert
```

### 4.2 验收挂规格编号（改造，G7）

- 验收表每行的“编号”必须是现役规格中已存在的验收编号（`acceptance.py` 已能解析），或写成 `新增:<规格文件>#<编号>`（同一批改动在规格里新增该编号，规格属 R2，会一并被用户审），或写 `不挂规格：<原因>`。
- 新需求先进规格、再进任务书。规格是现役合同，任务书只是一次交付（报告 4.3：大任务的规格“随代码沉淀在仓库”）。这样现有的“编号 ↔ 测试”映射自然覆盖到每个任务，不再出现任务 002–004 那样编号填“—”的情况。
- 每行标证据类型（单测 / 夹具 / 真实数据回放 / CI 断言 / 真机 UI）。真机 UI 类进入人工验收清单，不假装自动化（沿用方案 §2）。
- 按报告 4.2，完成定义覆盖四类：功能验收（验收表）；质量门禁（verify 全绿，默认包含，不必逐条写）；非功能约束（本项目主要是隐私与兼容性，如“诊断日志不含正文”，写进验收表）；文档与变更说明（用户可见的变更更新 README 或规格）。

### 4.3 按规模取用（保留报告 4.3 的分级）

| 规模 | 本项目的例子 | 任务书形态 | 用户审什么 |
| --- | --- | --- | --- |
| 小 | 补测试、修 lint、改文案 | 头部 + 一句终态 + 验收命令；多个小任务可以攒成一个 PR 一次审完 | 扫一眼终态与验收命令 |
| 中 | 有复现的缺陷、小功能 | 完整模板：终态、非目标、前置条件、验收表、步骤与提交顺序、风险与回退、预算、参考示例 | 验收表 |
| 大 | 新功能、跨模块改动 | 先改规格（需求与验收编号），再拆成多个中任务 | 规格与拆分 |

### 4.4 准入与澄清（新增 `harness/taskbook.py`）

派发前由 dispatch 调用，不通过即拒绝派发（报告 4.4：模糊需求在开工前消解，而不是在 PR 里消解）；同时进 verify default，对仓库中全部任务书检查：

1. 头部字段齐全，类别与风险取值合法且相容（例：K2 只允许 R0，K3 只允许 R1）；预算不超过上限（CI 轮次 ≤ 3、重试 ≤ 2，沿用现有模板）。
2. 验收表非空，每行有编号、证据类型；可自动化的行写明测试名或命令。
3. 中、大任务有非目标、前置条件、步骤与提交顺序、回退方式。
4. 任务书已在 main 上（即已经用户审过）。

澄清规则：执行方发现验收无法判定、前置条件不满足，或存在多个合理方案时，停下来提交“澄清”类升级包（第十三节），不得自行扩大或缩小范围。技术问题由设计方回答，涉及意图的交给用户（报告 4.4：把“澄清”设为正式步骤）。

### 4.5 模板改动与机器验收

- 保留：终态、非目标、前置条件、参考示例、升级包（报告 4.1、4.5）。
- 改造：加头部与“步骤与提交顺序”（计划并入，见第六节）；删去手填的“试跑记录”（改为自动生成，见第十一节）。
- 机器验收：缺头部、验收未挂编号、类别与风险不相容的样例任务书各被 `taskbook.py` 拒绝；执行方编辑任务书被守卫拒绝；改动 `docs/plans/task-*.md` 被 `risk.py` 判为 R2；历史任务 002–004 补齐头部或登记豁免后 verify 全绿。

## 六、环节 3：规划与派发——确定性流程包住智能体节点

报告依据：6.1–6.6、7.4、8.4、9.5。

|  | 设计 |
| --- | --- |
| 引导 | 任务书的“步骤与提交顺序”；派发流程固定；一个槽位一个任务 |
| 传感 | 每步之后的确定性检查；失败签名比对；运行记录 |
| 升级 | 准入不过、已被认领、未信任、超预算、打转、卡死即停 |

### 6.1 计划并入任务书（改造，G9）

计划模板从未被用过，实际由任务书承担（任务 004 写死了三个提交的顺序），效果尚可。改为：任务书增加“步骤与提交顺序”一节，每步写改哪些文件、怎么验证、对应哪条验收；删去“R2 以上先交计划”的要求，计划模板归档。报告 6.1 的“人审前两步”，在本项目就是用户审任务书的验收表与步骤。

### 6.2 派发脚本 `bin/dispatch`（新增，G1、G3、B7、B21）

派发是确定性节点，执行方只在“实现”和“按报错修复”两个智能体节点工作（报告 6.4：Stripe 的 blueprint 在确定性步骤与创造性步骤之间交替；Airbnb 每个文件走状态机，上一步验证通过才进入下一步）。

| 步骤 | 类型 | 做什么 | 失败时 |
| --- | --- | --- | --- |
| 1 准入 | 确定性 | `taskbook.py` 检查任务书，读取预算 | 拒绝派发，列出缺项 |
| 2 认领 | 确定性 | 向 origin 推送 `task/<编号>` 分支；远端已有即已被认领 | 停止，报告认领者 |
| 3 备环境 | 确定性 | 取一个空闲槽位（第七节），`fetch` 后从 `origin/main` 切出任务分支，清理未跟踪文件 | 无空闲槽位则排队 |
| 4 信任预检 | 确定性 | 按宿主检查槽位的项目钩子信任（如 `zcode hooks trust status`） | 未信任：停止，把授权命令交给用户，不代为授权 |
| 5 实现 | 智能体 | 以 Snowson 身份运行执行方，提示词由任务书与固定模板渲染 | 超时、卡死：终止并升级 |
| 6 本地判定 | 确定性 | 在执行方进程之外重跑 `bin/verify` | 未通过：带失败摘要回到 5，计入重试 |
| 7 推送与开 PR | 确定性 | 写入并提交本次运行记录，推分支，开 PR；PR 描述由脚本生成：任务、类别、验收编号、运行记录摘要、verify 摘要 | — |
| 8 等 CI | 确定性 | 轮询 build 结果，计 CI 轮次 | 失败且未超预算：带 CI 失败摘要回到 5；超预算：升级 |
| 9 收尾 | 确定性 | 归还槽位；合并与否交给第九节的策略 | — |

要点：

- **每次重试必须带新的外部信息**（报告 8.4）：回到第 5 步时，提示词附上 verify 或 CI 的失败摘要；连续两轮失败签名相同（同一测试、同一报错）视为打转，直接升级（报告 7.4：反复打转是要立即干预的信号）。
- **提示词入库**：渲染后的提示词只由任务书和模板生成、不含对话内容，随运行记录入库，PR 描述附哈希（G3；报告 9.5、7.6 要求记录模型与提示词版本）。提示词模板属 R3。
- **宿主支持**：OpenCode（`opencode run`）与 Pi（`pi -p`，须槽位已信任）可全自动；Zcode 只有桌面版执行工作区钩子，dispatch 对 Zcode 只做 1–4 步并生成提示词文件，由用户在桌面版打开槽位运行，6–9 步照常由脚本完成。
- **两种附加模式**：`bin/dispatch review <PR>` 在只读槽位里以评审提示词启动非设计方的 Agent（第八节）；`bin/dispatch --eval <编号> --repeat k` 跑评测集（第十一节）。

### 6.3 归属与并行（新增规则，G1 的另一面）

- **分支即认领**：任何 Agent（含设计评审方）开始一项工作前，先把自己的分支推到远端；远端已有同一任务的分支即已被认领。待办清单“负责”列写分支名。借鉴 Carlini 用 git 锁文件分配任务（报告 6.5）；2026-09-27 Codex 与 Claude Code 同时做同一份复评的冲突由此避免。
- **主工作目录只留给用户**（审计 1.3）：Agent 一律在槽位中工作，dispatch 拒绝在主目录启动执行方。
- **先单体，不并行改同一区域**：一个槽位同时只跑一个任务；两个任务的步骤涉及同一文件时由设计方串行派发（报告 6.5、6.6：先把单个 Agent 用足；多个 Agent 同时改同一区域却没有归属是常见错误）。

### 6.4 这个组件编码的假设

dispatch 假设“执行方不会可靠地自己控制预算、识别打转、如实收尾”（任务 002–004 的预算都靠自觉，试跑记录没人填）。若将来宿主原生提供等价的预算、隔离与记录，并且评测显示去掉后 pass^k 不降，就改为薄封装。

机器验收：用 dispatch 跑一个真实 K2 任务，PR 描述含运行记录摘要、主目录 `git status` 无变化；认领冲突、未信任、超时、打转四个样例各自按表中“失败时”一列处理（单测用假执行方模拟）。

## 七、环节 4：执行环境——限定最坏后果

报告依据：7.1–7.6、12.1–12.4。

|  | 设计 |
| --- | --- |
| 引导 | 槽位 worktree、Agent 身份、守卫白名单与确定性拒绝、任务预算 |
| 传感 | 计时、计数、卡死与打转检测；守卫拒绝计数 |
| 升级 | 超预算即终止，生成升级包 |

### 7.1 槽位 worktree（新增，G1）

- 在仓库同级目录建 3 个固定槽位（数量可配），用 `git worktree add` 创建。它们与主目录共享对象库和 `core.hooksPath`，git 层护栏自动生效。
- 选固定槽位而不是每任务新建目录：Zcode、Pi、Codex 的项目钩子信任按路径记录，未信任时命令照常执行、守卫静默失效（delivery-harness 规范的验证状态已实测）。固定路径让用户每个槽位只授权一次。
- 槽位是报告 7.1 说的“可丢弃环境”：每次派发都从 `origin/main` 重建分支并清理未跟踪文件；槽位坏了直接删掉重建。
- 这是**工作隔离**，不是**安全隔离**：同一 macOS 用户下，执行方仍能读用户目录与凭据（B10）。安全隔离的分阶段方案见第十二节。

### 7.2 身份与权限（保留 + 小改）

- 执行方经 `bin/as-agent` 以 Snowson 身份推送；dispatch 启动执行方前清除继承的 `GH_TOKEN`、`GITHUB_TOKEN` 等变量，只注入 Agent 令牌。
- 分层权限沿用三层护栏（报告 7.2）：Agent 层守卫（白名单 + 确定性拒绝）、git 层钩子、服务端 ruleset 与非推送者批准。报告中的“分类器”一层不引入：执行方宿主各异，确定性规则可测、可回放。
- 自动批准模式（如 `pi -a`）只允许在槽位中使用（报告 12.3：跳过权限只能在隔离环境内使用）。
- 守卫新增拒绝项（implementer 角色）：编辑任务书与规格（第四节）；编辑 `docs/runs/**`（运行记录由 dispatch 写）；关闭、删除议题或改 `escape`、`audit`、`escalation` 标签（第十四节）。

### 7.3 预算、熔断与卡死检测（新增，B7；报告 7.4）

| 预算 | 来源 | 谁执行 | 超限动作 |
| --- | --- | --- | --- |
| 时长 | 任务书 `wall_clock_min` | dispatch 计时 | 终止执行方（先 TERM 后 KILL），写升级包 |
| 重试 | `retries`（≤ 2） | dispatch 计数 | 停止并升级 |
| CI 轮次 | `ci_rounds`（≤ 3） | dispatch 计数，CI 的度量步骤复核 | 停止并升级；PR 打 `budget-exceeded` 标签，策略不再自动合并 |
| 卡死 | 15 分钟既无文件变化也无输出 | dispatch 监视 | 终止并升级 |
| 打转 | 连续两轮失败签名相同 | dispatch 比对 | 停止并升级 |
| token | `tokens`（宿主能报时） | 运行记录 | 只告警，进周报 |

CI 侧复核：`metrics.py` 已能统计分支上的 build 运行与失败轮次，改为与任务书预算比对。这样即使绕过 dispatch 手工派发，超预算也会被机器发现。按报告 7.4，预算要与质量收益权衡：初值沿用现有模板（CI ≤ 3 轮、重试 ≤ 2 次，比 Stripe 的 2 轮 CI 稍宽），季度按数据调整。

### 7.4 状态外置与长时运行（保留）

本项目的任务都能在一次运行内完成，不引入持久化执行框架（方案 §8 不上 Temporal）。状态在任务书、分支提交和运行记录中，中断后重新派发即可从分支继续（报告 7.3）。若以后出现跨多次运行的大任务，先拆成中任务（第四节），而不是延长单次运行。

### 7.5 非确定性与模型路由（新增；报告 7.5、7.6、10.5）

- 运行记录固定写入执行方宿主、版本、模型名；只在同一任务类别、同一配置内对比。
- 换执行方、换模型或改派发提示词模板，先在评测集上跑 pass^k（第十一节），不低于当前配置才切换。各角色用哪个模型，由评测数据决定，而不是外部的一次性对比结论（报告 7.5）。

机器验收：守卫测试覆盖三项新增拒绝；dispatch 单测覆盖超时、卡死、打转与超 CI 预算；超预算的样例 PR 被 harness job 标记且未被自动合并。

## 八、环节 5：验证与门禁——主控制器

报告依据：8.1–8.6、2.4、2.5。这一环最强，设计以补缺为主。

|  | 设计 |
| --- | --- |
| 引导 | 判定器与合同对执行方只读；完成定义写在任务书 |
| 传感 | 分层判定（计算型在前）+ 独立评审（推理型在后）+ 留出判定 |

### 8.1 分层判定（保留 + 补层）

| 层（报告 8.1） | 本项目的判定器 | 状态 | 何时运行 |
| --- | --- | --- | --- |
| 1 即时反馈 | ruff、卫生检查、守卫 | 保留 | 每次编辑或提交 |
| 2 功能测试 | Python 434 个用例；Swift 策略与运行器测试 | 保留 | verify default、CI |
| 3 架构适应度 | 架构测试；质量棘轮 | 改造：加 Swift | CI、每周 |
| 4 行为验证 | 黄金快照、真实格式夹具、真机 UI 人工验收 | 保留 | CI、人工 |
| 5 测试强度 | 6 组定向变异、性质测试、41 个回放 | 改造：回放强制 | CI、每周 |
| 6 语义评审 | 独立上下文评审 | 新增（试行） | R2 以上合并前 |
| 7 安全扫描 | 卫生检查（凭据、本机路径）+ GitHub 密钥扫描 | 改造：开密钥扫描 | 提交、推送 |

### 8.2 防作弊（保留 + 两处补强）

保留：执行方改不了判定器（守卫 + R3 路径）；已有测试按 base 版本运行；修复证据要求修复前断言失败；变异得分只升不降；最终判定在 CI 用 main 上的 harness 重跑（报告 8.3）。这些措施都不依赖提示词——报告 2.5 的数据表明，明确要求“不要作弊”后仍有 70–95% 的尝试在作弊。

补强：

1. **回放强制（G2）**：PR 中每个非文档类 `Defect:` 编号，head 上必须满足其一：`replay_cases.py` 有对应注入用例；有守卫测试（GUARDED）；登记为暂缓（DEFERRED）并写明原因。由 `evidence.py` 在 harness job 中检查，不满足即失败。v0.8.0 基线之后的新缺陷（如 H0926-7、-8）一视同仁。
2. **留出判定**：base 测试不是留出测试（执行方看得到）。真正的留出判定放在评测集：判定测试存在执行方看不到的位置，运行结束后才放入槽位执行（报告 8.3：保留一部分 Agent 看不到的验收测试；见第十一节）。

### 8.3 独立评审与校准（新增，G5、G6；报告 8.2、2.4）

- **分离规则**：R2 及以上的 PR，评审方必须不是该任务的设计方（任务书头部 `designer`），也不看执行方轨迹，只看任务书、diff 和 `review_pack.py` 证据包。Codex 设计的任务由 Claude Code 评审，反之亦然。这解决审计指出的“评审方同时是任务设计方”。
- **触发**：auto-merge 工作流判定为 R2 及以上时，除请用户评审外，再给 PR 打 `needs-independent-review` 标签；评审由 `bin/dispatch review <PR>` 在只读槽位里启动，结论以固定格式评论写回 PR：结论（通过 / 不通过 / 需用户验收）、发现列表、评审方与模型。
- **定位**：试行期内，评审结论只是给用户的输入，不替代用户审批（报告 8.6：是否全量人审取决于爆炸半径；报告十八节：高风险代码靠机审要达到什么可靠度尚无公认标准）。
- **校准**（报告 8.2、2.4：分别度量抓住问题的比例和放过好结果的比例）：建 `evals/review/` 校准集，初版约 25 个“已知有问题”的 diff（由 v0.8.0 的 R1–R19、X1–X6 与 H 系列缺陷还原）和约 15 个“已知良好”的已合并 PR。每次改评审提示词或换评审模型跑一遍，算**真阳率（TPR）**和**真阴率（TNR）**。另把每个试行 PR 的评审结论与用户最终决定、后续逃逸对照，累计一致率。报告建议每种失败模式 100–200 个标注样本，单人项目先从真实样本起步，随逃逸增长。
- **何时常态化、何时撤掉**：试行 3 个 R2 PR 后由用户决定是否常态化（审计 2.4）。它编码的假设是“测试抓不住需求偏离”（G6：H0926-7 就是验收映射只查测试存在而漏掉需求）。若 30 个 R2 PR 中独立评审没有发现任何用户也没发现的问题，降为抽样评审。

### 8.4 可合并高于测试通过（改造，G10；报告 8.5）

- **Swift 纳入质量棘轮**：不引入新依赖（确定性优先、工具少而准），在 `quality.py` 中用轻量解析统计 Swift 文件行数、函数长度与嵌套深度，基线入库、只降不升。若解析误差过大，再评估 SwiftLint（新依赖属 R3）。
- **无修改合并率**按第十四节的定义统计，是“可合并”的综合信号，不是门禁。

### 8.5 有界重试（改造）

预算从“写在任务书、靠自觉”变为 dispatch 与 CI 双重计数（第七节）。超限即停，转升级包（报告 2.6 异常即停、8.4）。

机器验收：带新 `Defect:` 但无回放的样例提交使 harness job 失败；故意加长的 Swift 函数样例使棘轮失败；校准集跑出的 TPR、TNR 入库；3 个试行 R2 PR 上有非设计方的结构化评审结论。

## 九、环节 6：集成与发布——小批量、主干常绿、可重发

报告依据：9.1–9.5、2.9、8.6。

|  | 设计 |
| --- | --- |
| 引导 | 一个任务一个 PR；规模阈值；严格必过检查；发版需用户审批 |
| 传感 | `policy.py` 逐条判定并写理由；发版后观察窗口 |
| 升级 | 任一条不满足即转用户；发版出问题即重发上一版 |

### 9.1 小而短命的 PR（保留 + 阈值）

- 一个任务一个 PR（保留；现状改动行数中位 66，开到合并中位约 11 分钟）。
- **规模阈值**：增删行数（不计黄金快照与运行记录）超过 400 行的 PR 不自动合并，转用户并提示拆分。报告 8.6 把“diff 超过规模阈值”列为路由给人的信号；报告 9.1 引 Faros：PR 规模变大是危险信号。审计中 40 个 PR 有 4 个超过 400 行。阈值写在 `autonomy.toml`。

### 9.2 主干常绿（改造，C2）

- ruleset 的必过检查改为严格模式：PR 必须基于最新 main 通过 build 与 harness 才能合并。
- 报告 9.2 建议生产主干用合并队列，方案 §8 已决定不上。单人仓库并发 PR 少，严格模式能以最小代价保证“合入后仍全绿”；代价是 PR 落后时需同步重跑，审计估计很少发生。
- 不稳定测试：CI 失败后重跑即通过的，记为疑似不稳定，进周报并单独修，避免它误导执行方重试（报告 9.2）。

### 9.3 合并路由（新增 `harness/policy.py`；报告 8.6、9.3）

auto-merge 工作流的判定步骤从“只看风险等级”改为调用 `policy.py`，仍在 main 上执行、只把 PR 当数据读（沿用现有设计）。按顺序判定，任一条不满足即转用户评审：

1. **停机开关**：仓库变量 `AUTO_MERGE_ENABLED` 不为 `true`（第十节）。
2. **风险**：`risk.py` 判为 R2 及以上。
3. **类别**：机器按路径、trailer 与证据判定的类别，在 `autonomy.toml` 中不是 L4；任务书声明的类别与机器判定不一致，按“未分类”处理。
4. **预算**：该类别滑动窗口内的逃逸超过误差预算（第十四节）；或本 PR 带 `budget-exceeded` 标签。
5. **规模**：超过 400 行。
6. **运行记录**：来自 `task/*` 分支却没有合格的运行记录（第十节）。

全部满足才由 App 批准并合并（沿用 D3）。被抽中的 K3 PR 合并后自动开 `audit` 议题（第十五节）。每条的判定结果与理由写进 job summary，“为什么自动合并了、为什么没有”都可追溯。

### 9.4 发版与回退（改造，B2、B19；报告 9.3、9.4）

本项目是以 zip 分发的 macOS 桌面 App，没有服务端，报告的金丝雀与自动回滚不适用，改为等价做法：

| 报告做法 | 本项目等价物 |
| --- | --- |
| 金丝雀 / 分批 | **自用先行**：发版前，待发版本对应的 main 开发包已在用户本机运行至少 3 天，期间没有新登记的逃逸 |
| 发布审批 | tag 触发 release job，`release_check.py` 核对版本号，environment `release` 由用户批准（保留；首次发版时实测） |
| 自动回滚 | **重发上一版**：保留上一版 zip 下载；回退 = 把上一版重新标为最新发布，并在发布说明中注明原因；书面步骤写入 delivery-harness 规范 |
| 部署后监控 | 14 天观察窗口（第十节） |

版本号仍须用户确认后才能打 tag，Agent 不打 tag、不发版（AGENTS.md）；预演、备份、变更窗口等 R3 发布要求对本项目即“用户审批 + 自用先行 + 可重发”。

### 9.5 可追溯（新增，G3；报告 9.5）

每个 PR 可以从三个方向追到源头：任务（任务书编号、验收编号）、运行（执行方、模型、提示词哈希、轮次）、判定（CI run 链接、证据包）。任务分支上的提交带 `Task:` trailer（派发提示词要求，harness job 检查）；运行记录只校验存在与格式，不当作正确性证据——正确性只认 CI。

机器验收：`policy.py` 单测覆盖 6 条判定分支与“全部满足”；实测一个 401 行的 R0 PR 被转用户；ruleset 严格模式由 `gh api` 读取确认并记入规范的验证状态。

## 十、环节 7：运行与观察——看得见，停得住

报告依据：10.1–10.6。“运行”在本项目有两层：交付系统本身（执行方运行、CI、自动合并），和发版后的 App。

|  | 设计 |
| --- | --- |
| 引导 | 停机开关与演练；观察窗口的定义 |
| 传感 | 运行记录；GitHub 失败通知；周报突变标红；逃逸登记 |
| 升级 | 关开关、误差预算降级、重发上一版 |

### 10.1 运行记录（新增，G3；报告 10.1、9.5、7.6）

每次派发生成 `docs/runs/<任务编号>/<尝试序号>.json`，由 dispatch 在执行方退出后写入，随该次推送一起提交（R0 路径）。字段名对齐 OpenTelemetry 的 GenAI 语义约定，便于将来接入，但不引入其基础设施（方案 §8；报告 10.1 也指出该约定仍处于“开发中”）：

| 字段 | 含义 |
| --- | --- |
| `task`、`class`、`attempt` | 任务、类别、第几次尝试 |
| `gen_ai.agent.name`、`host_version`、`gen_ai.request.model` | 执行方宿主、版本、模型 |
| `prompt_sha256`、`prompt_path` | 渲染后的提示词 |
| `started_at`、`ended_at`、`exit` | 时长与退出方式（正常 / 超时 / 卡死 / 打转） |
| `retries`、`failure_signatures` | 本地重试次数与每轮失败签名 |
| `guard_denials` | 守卫拒绝次数，按规则编号计，不含命令全文 |
| `gen_ai.usage.input_tokens`、`output_tokens`、`cost` | 宿主能报时填写 |
| `missing_context` | 执行方回报的缺失上下文或工具 |
| `escalation` | 升级类型与去向 |

- **不回写**：CI 轮次、合并状态、评审结论由周报从 GitHub 读取，不写回分支——每次回写都是一次新推送，会触发新一轮 CI、作废已有批准。
- **隐私**：只存结构化摘要，不存对话正文、输入内容或凭据（AGENTS.md 的诊断日志约束）；完整轨迹留在本机被忽略的 `build/runs/`，保留 30 天，供错误分析按需读取。
- **吃自己的狗粮（可行性待验证）**：本 App 本身就采集 OpenCode、Pi 等会话的状态与 token 用量。若按槽位路径与时间窗能把会话归到任务，运行记录的 token 与费用可以取自 App，用户也能在收件箱与桌面组件里看到正在跑的执行方——正是报告 10.6 说的“让人能看见并能干预”。先做一次验证：对一个已完成任务，App 汇总的 token 与宿主自报偏差在 10% 以内即采用。

### 10.2 停机开关（新增，G4；报告 10.3）

- 仓库变量 `AUTO_MERGE_ENABLED`（默认 `true`）。用户在 GitHub 网页（手机也可）改为 `false`，下一次判定起一律转人审（2026-09-28 修订：不开发此变量，改用 GitHub 自带的 Disable workflow，见第十七节）。正在运行的执行方由用户在本机 `bin/dispatch stop --all` 终止。
- 变量只有仓库管理员（用户）能改，Agent 账号无此权限。
- 停机与恢复步骤写入 delivery-harness 规范；每季度演练一次：关开关 → 开一个 R0 测试 PR → 确认被转人审 → 恢复。演练通过是 L5 的前提之一（报告 10.3：没有紧急停机开关，就不应进入 L5）。
- 按误差预算自动降级是第二道闸，见第十四节。

### 10.3 告警（新增；报告 10.2）

不上告警平台，用两类通道：

- **即时**：GitHub 自带的失败通知（CI、auto-merge 工作流失败）；dispatch 升级时以带 `escalation` 标签的 PR 评论或议题通知用户。
- **每周**：周报（第十四节）对比前 4 周中位数，以下信号突增一倍以上时在顶部标红：重试与 CI 轮次、守卫拒绝、升级数、被改动的已有测试、逃逸登记；pass^3 下降超过 0.1 同样标红。报告 10.2：告警针对突变而不是绝对值；分类器或守卫拦截是健康信号，不是故障。

### 10.4 发版后观察（新增，C5、B19；报告 10.6）

- 观察窗口：发版后 14 天。
- 信号：用户日常使用；App 已有的来源健康字段；诊断日志中的错误计数（日志本身不含正文）。
- 发现问题即登记逃逸议题，标注引入它的 PR；需要回退时按第九节“重发上一版”。
- 变更失败率按发版计：14 天内需要重发上一版或紧急修复版的发版占比。

### 10.5 Agent 参与运维：读多写少（保留；报告 10.4）

本项目无生产服务。Agent 可以读 CI 日志、运行记录、发布列表（放行只读 `gh release list/view`），不能创建或修改发布、不能改仓库设置与变量。

机器验收：缺字段或含违禁内容（如命令全文、本机路径）的运行记录样例被 harness job 拒绝；停机开关实测记录入规范；首次发版的 14 天观察记录入库。

## 十一、环节 8：反馈与改进——“持续”来自复利

报告依据：11.1–11.5、15.1、7.5。

|  | 设计 |
| --- | --- |
| 引导 | 沉淀形式的优先级（检查 > 脚本 > 评分标准 > 文字说明）；每个组件写明假设 |
| 传感 | 每周错误分析；评测集 pass^k；质量趋势 |
| 升级 | 沉淀项进待办；季度复盘决定升级、保持或收紧 |

### 11.1 每周错误分析（新增节奏；报告 11.1）

周一 quality 工作流生成周报后，由不是本周主要设计方的评审方做一次错误分析，用户花约 15 分钟读结论：

1. **素材**：本周全部异常——失败或超预算的运行、升级、CI 失败、守卫拒绝、评审发现、逃逸。单人项目每周量不大，全部都看（报告建议每周至少 10–20 条）。
2. **开放编码**：逐条写下问题，不预设分类。
3. **轴向编码**：归入现有失败分类（基线评审的 F1–F7、X1–X6），归不进去的新建类别，统计频次；判定用“通过 / 不通过”二元标准。
4. **决定沉淀形式**（报告 11.3）：能自动检查的写成守卫、lint 或架构测试；重复流程写成脚本或 dispatch 节点；判断标准写进评审清单并加校准样本；背景知识写进 AGENTS.md 或分目录说明；失败案例进评测集与回放集。能写成计算型检查的，不只写成文字规则。
5. **产出**：每个沉淀项进待办清单，编号、预计风险等级齐全；分析结论存 `docs/review/weekly/<年-周>.md`（R0），下一次分析和换人都能接上。

### 11.2 评测集与 pass^k（新增，B17；报告 11.2、15.1、7.6）

- **来源**：真实失败和真实任务，不造题（报告 11.2：从真实失败中抽 20–50 个简单任务开始）。初版约 20 个：v0.8.0 的 R1–R19 中能在历史提交上重现的缺陷修复（K4），加上 trial-001、任务 002–004 这类补测试与小功能任务（K2、K5）。
- **结构**：`evals/tasks/<编号>/` 存任务书、`base_sha`、类别；判定测试存 `evals/graders/`，派发时不放进槽位，运行结束后才拷入执行——这就是留出判定。
- **运行**：`bin/dispatch --eval <编号> --repeat 3`，每次试验用干净槽位（报告 11.2：避免共享状态造成相关失败），按类别算 pass^3 与 pass@3，评结果不评路径。
- **用途**：①换执行方、模型或提示词模板前后对比（报告 10.5）；②类别升到 L4 的证据（第十五节）；③换模型后检验哪些 harness 组件已不再承重（报告 7.5、11.5）。
- **读法**：在门禁完整的 L4 下，失败的运行不会合并而会升级，所以 pass^k 低主要意味着人的注意力成本高（值不值得放权）；安全与否看逃逸率（安不安全放权）。两者都达标才升级。
- **成本控制**：全量约 60 次运行，只在上述三种时机跑；平时每周抽 5 个任务各跑 1 次做回归哨兵。每次运行的费用记入运行记录，全量跑前先估算。

### 11.3 回放与台账（改造）

- 每个逃逸缺陷登记后，修复 PR 必须带 `Defect:` 与回放或守卫测试（第八节回放强制），并在评测集中加一个复现任务（报告 11.2：把每次事故、每个逃逸缺陷都转成一条回归评测用例）。
- 缺陷编号保持全局唯一（保留）。

### 11.4 试跑记录自动化（改造，G12）

任务模板中手填的“试跑记录”表改由周报从运行记录、PR 与议题自动汇总：评审轮次、CI 轮次、升级次数、人工介入、逃逸，与 v0.8.0 基线并列。任务 002–004 由评审方补一次历史数据，之后不再手填。

### 11.5 熵治理与定期重审（改造；报告 11.4、11.5）

- 每周 quality 工作流：变异、回放、复杂度棘轮（加 Swift）、文档新鲜度。先核对 2026-09-28（周一）的定时触发是否生效（审计 3.5）。
- 每月一次清理：由周报的复杂度热点生成 K3 类任务（行为不变重构），走 dispatch，按 K3 的策略合并。这就是报告 11.4 的“垃圾回收”；K3 升到 L4 之前由用户批准。
- 每季度或每次换执行方模型后：逐个组件核对它编码的假设是否仍成立（本设计各节写明了假设与删除条件），并按类别复盘误差预算，决定升级、保持还是收紧。

机器验收：评测集 ≥ 20 个任务且每个都能在 `base_sha` 上复现“判定失败”、在原始修复上“判定通过”（判定器自身被检验）；当前执行方配置的 pass^3 按类别出现在周报中；第一份每周错误分析入库。

## 十二、横切：安全与权限——用结构划边界

报告依据：2.8、12.1–12.6。原则：安全边界必须在 Agent 出错时依然成立。

### 12.1 按“三者最多取二”设计每类会话（C4；报告 12.1）

A = 处理不可信输入，B = 访问敏感系统或私有数据，C = 改变状态或对外通信。

| 会话 | A | B | C | 组合与约束 |
| --- | --- | --- | --- | --- |
| 执行方（实现） | 去掉：输入只有用户审过的任务书与仓库代码；不处理外部 issue 或 PR 评论；宿主可配置时关闭网页抓取工具；依赖只按锁定清单安装 | 有（含残余：同一 macOS 用户能读用户凭据，B10） | 有：只能推 `task/*` 分支、开 PR | B + C |
| 评审方（独立评审） | 有：执行方写的 diff 与说明视为不可信 | 只读仓库 | 去掉：只写评论，不推代码、不批准、不合并 | A + B |
| 设计方（调研、写任务书与 harness） | 有：网页调研 | 有 | 有：推分支 | 三者俱全 → 产出只能落在需用户批准的路径（任务书、规格 R2；harness、CI R3）或无运行时影响的 R0 文档，不持有合并与发版权限。报告 2.8：三项都需要时，至少要有人工审批或其他可靠验证 |
| auto-merge 工作流 | PR 内容（只当数据读，不执行 PR 代码） | App 私钥（只在允许 main 的 environment） | 批准与合并 | 判定代码来自 main，不可信输入无法触发有后果的动作（报告 12.1 引述的抗注入原则） |
| release job | — | 发布凭据 | 发布 | 用户审批 |

### 12.2 凭据与隔离的分阶段方案（B10；报告 12.2、7.1）

- **现在**：明确接受并写明残余风险——执行方与用户同一 macOS 用户，靠 Agent 层守卫、git 层钩子和服务端（非推送者批准、App 凭据隔离）兜底。Agent 账号按最小权限设置：能推分支、开 PR、评论、开议题，不能改设置与变量。
- **进入 L5 或扩大无人值守前（必须）**：给执行方单独的 macOS 用户，槽位放在该用户目录下，用户的 gh 凭据、钥匙串、SSH 密钥对其不可见；宿主支持时同时开文件系统与网络沙箱（报告 7.1：两者缺一不可）。
- 自动批准模式只在槽位中使用，dispatch 在主目录拒绝启动执行方（报告 12.3：Nx s1ngularity 事件中，投毒的 npm 包正是借用开发机上开了跳过权限的 AI 命令行工具搜刮密钥）。

### 12.3 密钥扫描与供应链（G13）

- 用户在仓库设置中开启 secret scanning 与 push protection（公开仓库免费，约 2 分钟）。
- 开发依赖锁版本，改依赖属 R3（保留）；Dependabot 价值低，暂缓（审计 2.9）。
- CI 令牌最小权限：各 workflow 已按 job 声明 permissions（保留；报告 12.3 引 Amazon Q 扩展事件：权限过宽的 CI 令牌被利用）。

### 12.4 破坏性动作硬拦截（保留；报告 12.4）

守卫与 git 钩子拒绝改写历史、推 main 与 tag、强推、删除受保护分支、合并与批准 PR、设置覆盖变量；服务端 ruleset 在本机两层都被绕过时兜底。覆盖变量只供人使用。新增拒绝项见第七节。

### 12.5 用 OWASP Agent 应用十大风险核对（报告 12.5）

| 风险 | 本设计的对策 |
| --- | --- |
| 目标劫持 | 执行方不处理外部输入；合同只读；评审方不能改代码 |
| 工具滥用 | 守卫按命令结构拒绝；工具少而准 |
| 身份与权限滥用 | Agent 单独账号；非推送者批准；App 凭据只在 main 的 environment |
| Agent 供应链 | 依赖锁定、改依赖 R3；守卫钩子改动需用户重新信任 |
| 意外代码执行 | auto-merge 不执行 PR 代码；CI 按 job 最小权限 |
| 记忆与上下文投毒 | AGENTS.md、任务书、规格属 R2 以上，改动需用户审 |
| Agent 间通信不安全 | Agent 之间不直接通信，只经仓库文件与 PR 交接，全部可审计 |
| 级联故障 | 停机开关；误差预算自动降级；一个槽位一个任务 |
| 利用人对 Agent 的信任 | 不采信自述，只认 CI 与证据包 |
| 失控 Agent | 预算、卡死与打转检测；槽位可丢弃 |

### 12.6 不引入自动审批分类器（报告 12.6）

报告 12.6 指出分类器对真实“过度热心”动作仍有 17% 漏判，需与沙箱、硬拒绝、最小权限叠加。本项目执行方宿主各异，先用确定性拒绝规则加服务端兜底；将来若某个宿主的分类器可用，只作为叠加层，不替代任何现有层。

## 十三、横切：人的角色与升级——从逐条审批到设计与例外

报告依据：3.1、13.1–13.5、2.7。报告 13.2：逐条审批既耗人又抓不住问题（用户批准 93% 的权限提示，对照实验中人工只拦下 13.6% 的危险命令），所以本设计不让用户逐条审批命令，只让用户审合同、证据与例外。

### 13.3 升级包（保留 + 结构化；报告 13.4）

- 沿用模板的五项：目标与当前状态、已尝试的方案及结果、证据、可选方案与推荐、需要人决定的具体问题。
- 改造：dispatch 升级时自动预填前三项（运行记录、失败摘要、CI 链接），执行方只写后两项。
- 升级以带 `escalation` 标签的 PR 评论或议题发出；处理人处理后打 `escalation:needed` 或 `escalation:unneeded`，周报据此算**升级精度**与**处理时长**。精度太低会把人拖回审批疲劳；接近 100% 则可能说明门槛过高、漏掉了该升级的情况。

### 13.4 人的注意力预算（报告 3.1）

| 优先级 | 投在哪里 | 形式 | 初始目标（每周） |
| --- | --- | --- | --- |
| 1 | 意图与验收 | 审任务书、规格、待办（R2） | 30–60 分钟 |
| 2 | harness 设计 | 审 R3 PR；季度重审 | 随实施阶段变化 |
| 3 | 高风险任务的计划 | 审中大任务的验收表与步骤 | 含在第 1 项 |
| 4 | 升级与告警 | 只处理系统送来的例外 | ≤ 30 分钟 |
| 5 | 抽样审计 | R1 抽审、读周报与错误分析结论 | 15–30 分钟 |

这些是初值，用来与周报里实测的“每小时人工注意力产出的合格交付”对照（第十四节）。

### 13.5 技能保持与信任校准（报告 13.5、2.7）

单人项目不做轮岗（审计判为不适用）。保留两条轻量做法：每月读 2 条执行方完整轨迹；季度停机演练由用户亲手做。报告 2.7 引 Bainbridge：越少需要人工干预的系统，越需要投资于人的训练。放权与否只看数据，不看感受（报告 13.5：METR 试验中感觉快 20%，实际慢 19%）。

## 十四、横切：度量与误差预算——用数据决定放权

报告依据：15.1–15.4、2.6、10.2、10.3。六类指标共同回答一个问题：还能不能再放手一点。

### 14.1 指标定义（本项目口径）

| 类别 | 指标 | 本项目的定义 | 数据来源 |
| --- | --- | --- | --- |
| 质量 | 无修改合并率 | R2 以上 PR 中：首次请求评审后没有新提交、用户未要求修改即合并的比例。R0/R1 自动合并按流程必然“无修改”，不计入（审计 2.11） | PR 事件 |
| 质量 | 逃逸缺陷率 | 合并后登记的逃逸 ÷ 同类别合并数（滑动窗口） | `escape` 议题 |
| 质量 | 变更失败率 | 按发版：14 天内需重发上一版或紧急修复的发版占比 | 发布记录 + 议题 |
| 质量 | 复杂度趋势 | Python 与 Swift 质量棘轮的周增量 | quality 工作流 |
| 质量 | 变异得分 | 6 组定向变异得分 | `mutate.py` |
| 稳定 | pass^3 / pass@3 | 评测集按类别计 | `bin/dispatch --eval` |
| 效率 | 合格交付数 | 合并且 14 天内无回退、无归因逃逸的 PR 数 | PR + 议题 |
| 效率 | 交付周期、CI 轮次 | 派发到合并的时长；达到全绿的 build 轮次 | 运行记录 + Actions |
| 自治 | 人工干预率 | 每个任务中用户的手工修改、要求修改、手工重跑次数 | PR 事件 |
| 自治 | 升级率、升级精度、处理时长 | 见第十三节 | `escalation` 标签 |
| 自治 | 人审覆盖率 | 按风险等级统计的人审 PR 占比 | PR 事件 |
| 成本 | 每个合格交付的成本 | token 费用 + 估算的人工分钟 | 运行记录 + 用户动作计数 |
| 安全 | 守卫拒绝数与类型 | 按规则编号 | 运行记录 |

人工时间的估算：按用户动作计数乘标准分钟（批准 3 分钟、带修改意见的评审 15 分钟、处理升级 10 分钟、抽审 5 分钟），每月由用户校正一次标准分钟。这是近似值，只用于看趋势。

### 14.2 北极星与护栏（报告 15.3）

- **北极星**：每小时人工注意力产出的合格交付数。它同时奖励“产出多”和“占用人少”。
- **护栏**：① Agent PR 的逃逸不超过误差预算；② 评测集 pass^3 不低于该类门槛；③ 变更失败率不高于基线期（v0.8.0，基线评审 §2）的水平。报告的护栏是“Agent 变更失败率不高于人工基线”，本项目几乎没有人工交付的对照组，故以基线期代替。

### 14.3 误差预算（新增；报告 2.6、10.3）

| 类别 | 窗口 | 预算（初值） | 超支后 |
| --- | --- | --- | --- |
| K1 说明与记录、K2 补测试 | 最近 20 次合并 | 逃逸 ≤ 1 | 该类自动合并关闭、转用户审，直到用户改 `autonomy.toml` 恢复 |
| K3 行为不变重构 | 最近 10 次合并 | 逃逸 = 0 | 同上 |
| K4–K6（R2） | 最近 20 次合并 | 逃逸 ≤ 2 | 合并方式不变（本就人审）；触发该类的错误分析专项，独立评审改为必做 |

- **逃逸的定义**：合并后才发现、本应被门禁或评审拦住的缺陷，归因到引入它的 PR 与类别。
- **登记**：任何人（包括 Agent）发现后开带 `escape` 标签的议题，写明引入的 PR。登记只会让系统更保守，所以不设门槛；执行方的守卫拒绝关闭、删除议题和改标签；统计时已关闭的议题照样计数。议题公开可见，内容不写会话正文。
- **生效**：`policy.py` 在每次合并判定时用只读 API 读窗口内的逃逸数，即时降级，不等人。
- **漏检率只能抽样估计**（报告 15.4）：K3 的抽审与 K1、K2 的季度抽样（第十五节）是“零逃逸”是否只是“零发现”的唯一检验。

### 14.4 周报（新增，B30）

`quality.yml` 每周一运行，新增一步 `harness/weekly.py`：从运行记录、PR、议题、Actions 汇总 14.1 的指标，写入固定的“每周质量报告”议题（手机上可读），对突增信号标红（第十节），并列出各类别误差预算的消耗与升级条件的达成情况。周报只读数据、不改策略。

### 14.5 度量陷阱（报告 15.4）

- 不看 PR 数和代码行数。
- 同类别内比较，不跨类别比。
- 不用感受代替测量；样本少时只报计数、不报比例。

机器验收：手动触发一次 quality 工作流，周报议题包含 14.1 全部指标项（数据不足的标“样本不足”）；注入一组突增数据的测试用例被标红；登记一个测试用逃逸后，K2 的下一个 PR 被转用户，关闭该议题后仍计数。

## 十五、自治等级与放权规则

报告依据：1.1、16.1、16.2、10.3、11.5。自治是设计决定，不是能力的副产品；同一时间，不同任务类别处在不同等级。

### 15.1 任务类别

类别由机器按改动路径、trailer 与证据判定，任务书的声明只用于交叉核对（与风险等级“不由执行者自报”一致）。可验证性按报告 2.3 的标准判断：是否有快速、客观、低噪声的判定器。

| 类别 | 本项目的典型任务 | 判定器 | 可验证性 | 风险 |
| --- | --- | --- | --- | --- |
| K0 合同 | 任务书、规格、模板、待办清单 | 准入检查、验收映射 | 中：格式可判，内容靠人 | R2 |

### 15.3 规则

1. **升级人定**：只有用户能改 `harness/autonomy.toml`（R3），升级 PR 必须附周报中的证据（上表“升级所需证据”）。
2. **降级自动**：误差预算、停机开关、CI 预算超限由 `policy.py` 在每次判定时即时生效。
3. **按类别，不一刀切**（报告 1.1）。
4. **抽样审计**：K3 升到 L4 后，按 PR 编号哈希每 3 个抽 1 个，合并后自动开 `audit` 议题；K1、K2 每季度随机抽 5 个已合并 PR。抽审发现问题记为逃逸（报告 9.3：R1 = 自动合并 + 抽样审计）。
5. **季度复盘**：每季度（或换执行方模型后）按类别复盘误差预算消耗，决定升级、保持或收紧（报告 11.5）。

### 15.4 L5 与 M3 的门槛

本设计的 90 天目标是 M2：K1、K2 在 L4 且有数据支撑，K3 按规则完成一次升级或明确不升；不进入 L5。进入 L5（例如只提 PR 的后台维护 Agent 定期做文档对齐或清理，报告 11.4）前必须同时满足（对应报告 16.2 的 M3 准入）：

- 护栏指标连续 4 周达标；
- 停机演练通过；
- 执行方单独系统用户与沙箱就位（第十二节）；
- 回放集中的注入类用例在后台 Agent 的配置下全部被拦（代替报告中的安全红队测试）。

| 轮岗与资深带初级（13.5） | 月读轨迹 + 季度演练 | 单人项目 |
| 人工基线对照（15.3） | 以 v0.8.0 基线期代替 | 几乎没有人工交付的对照组 |

### A.3 十二条反模式的防线（报告 17.1）

| 反模式 | 本设计的防线 |
| --- | --- |
| 用提示词代替结构约束 | 所有新规则落为守卫、CI 检查、ruleset（一） |
| 只看“测试通过” | 多维门禁 + 独立评审 + 无修改合并率（八、十四） |
| 自己评自己 | 非设计方评审、不看执行方轨迹、校准（八） |
| 把逐条人工审批当安全机制 | 守卫 + 服务端 + 例外升级；人只审合同与证据（十三） |
| 在存有密钥的开发机上长期跳过权限 | 自动批准只在槽位；L5 前单独系统用户（十二） |
| Agent 能直接写生产 | Agent 不能打 tag、不能发版；发版需用户审批（九） |
| 一次做完大任务 | 大任务先改规格再拆成中任务；一个任务一个 PR（四、六） |
| 大 PR、长分支 | 400 行阈值；严格检查（九） |
| 只追吞吐不管熵增 | Swift 进棘轮；月度清理；复杂度趋势进周报（八、十一） |
| 无限重试 | dispatch 与 CI 双重计数；打转检测（七） |
| 平级多 Agent 抢同一块代码 | 分支即认领；一个槽位一个任务；同区域串行（六） |
| 凭感觉决定放权 | 升级必须附周报证据；降级自动（十五） |
