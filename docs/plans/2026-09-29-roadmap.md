# 路线与已定设计（2026-09-29）

状态：现役。来源：用户与设计评审方（Claude Code）2026-09-29 在 Agent-Notification 会话中对齐并批准的方案；阶段 A、B 已完成（delivery-harness #1、Agent-Notification #66）。待办编号见 [backlog.md](../backlog.md)。

## 1. 已定决定（不要重新讨论）

- **独立仓库**：`SnowsonZ/delivery-harness`，公开，MIT；名称取「可验证交付」（delivery），不用 agent-harness、product-harness。
- **安装形态**：带锁文件的内置副本（`.harness/engine/` + `.harness/engine.lock`，integrity 检查）。理由：守卫的可信来源是「经用户批准合并到 origin/main 的代码」，内置副本与此同构。放弃 pip/uv（在执行方可写的环境里、不在 main 上）、git submodule（`git archive` 不含子模块）、可复用 workflow（CI 与本机两个来源）。详见 Agent-Notification `docs/decisions/0001-harness-extraction.md`。
- **面向开源**：引擎与模板不含任何使用者自己的值；能探测的探测，探测不到的问一次写进配置；缺必填配置明确报错，不回落到任何人的默认值。
- **顺序**：先让第三方能照 README 走通（B48）→ 可观测性 v0.2（B46，设计先交用户审）→ 接入无感化与 TypeScript 插件（B45）→ 装进第二个项目。第二个项目为 Python + TypeScript，协作环境与 Agent-Notification 相同（GitHub + ruleset、Agent 账号 + 批准 App、Pi 执行、OpenCode 评审）。
- **不做常驻守护进程**：评审由设计方在会话中后台触发，升级提醒放 CI，保留期清理顺带做。无人值守需要先做停机演练，等数据证明需要再加。
- **不接入 Agent-Notification 收件箱**：「待批准」靠 GitHub 通知。
- **批准 App 不改装为「所有仓库」**：把新仓库加入 App 并进接入时用户执行的那一条平台命令。

## 3. 接入与使用无感化（B45、B48 的验收基准）

目标：用户在一个项目里只剩「说一句话 + 批准」。必须由人做的只有授权（平台安全设置、钩子信任）、批准（R2 以上 PR、升级、放权）、定版本号，每类压缩成一次点击或一条命令。

| 时机 | 用户做什么 | 自动完成 |
|---|---|---|
| 每台机器一次 | 一条引导命令：拉取引擎、安装全局技能 `delivery-harness`（按用户全局规则装到 `~/.agents/skills/`，副本留 `workspace/agent/skills`，Claude Code 用符号链接） | 引导命令 |
| 每个项目一次 | 对设计方 Agent 说「给这个仓库接入 harness」 | 技能执行 `adopt` |
| 每个项目一次 | 核对并批准接入 PR；执行 PR 里给出的一条平台命令（ruleset、secrets、Agent 协作者邀请、把仓库加入批准 App） | Agent 账号自动接受邀请；`verify` 检查平台设置是否齐全 |
| 每个项目一次 | 首次启动 Claude Code 时确认项目钩子（Pi 以 `-na -e` 加载守卫，不需要信任） | — |
| 日常 | 提需求；批准 R2 以上 PR 与升级 | 设计方按受管块工作，CI 负责判定、路由、升级提醒与告警 |

`adopt` 要点：

- 探测语言、源码目录、测试与 lint 命令、运行时、规格与任务书目录，结果列在接入 PR 里供核对。
- 默认值：风险分级按通用布局；`autonomy.toml` 全部人审；棘轮基线取当前值；回放与变异目标为空。
- 渐进档位 `starter | standard | full`，starter 下验收映射与任务书准入只警告。
- 已有 `.claude/settings.json`、`.codex/hooks.json`、CI 幂等合并；AGENTS.md/CLAUDE.md 插带标记的受管块。

第三方需要的身份：仓库所有者、一个单独的 Agent 账号（`checks.toml [identity] agent_login`，`bin/as-agent` 按它向 gh 取令牌）、可选的批准 App（自己建，只用于 R0/R1 自动合并）。只有一个账号的开发者走单账号模式（B48，写明风险）。

## 4. 可观测性设计要点（B46，实现前先写设计文档交用户审）

已有：派发运行记录（字段按 OTel GenAI 命名）、每轮原始事件流、各脚本的 step summary、评审评论、周报突变标红。缺口：没有统一事件模型与贯穿全程的追踪 ID；只记派发链路（设计方操作时的守卫拒绝、verify 各检查、路由理由没留存）；异常只有周报。

- **事件契约**：`ts`、`trace_id`（任务+尝试，或 PR+head）、`stage`、`step`、`status`（ok/fail/skip/deny/error）、`duration_ms`、`inputs`/`outputs`（只存 ID、哈希、计数）、`error{kind, signature}`、`actor{role, host, model}`、`engine_version`；字段按 OTel 语义命名，不引入依赖。
- **追踪 ID**：dispatch 生成，写进运行记录与 PR 正文，CI、review、policy 读回。
- **埋点**：`emit()` 包住现有结构化结果（verify 的 Result、policy 理由、review 的 Verdict、dispatch 各步、守卫决定），不改判定逻辑。
- **写到哪里**：本机 `<git common dir>/harness/events/*.jsonl`（30 天，收 B40）；CI 上传 artifact、step summary 由事件渲染；运行记录加阶段时间线与 `missing_context`（收 B36），`run-check` 加内容违禁检查（收 B38）。
- **查询与告警**：`bin/harness trace <任务|PR>`、`bin/harness events`；卡死、超预算、评审否决、完整性失败、守卫拒绝突增时 PR 评论加 `escalation` 标签；周报改为从事件汇总。
- **隐私**：只存管理所需元数据，不放命令全文、本机路径、会话正文。

## 5. 验收方式

- 引擎改动：本仓库 ruff 与 unittest；涉及判定、守卫、派发、配置读取时，装进 Agent-Notification 的 worktree 跑 `bin/verify --full`，以「测试数、质量指标、变异得分不变」作为等价证据。
- 第二个项目接入：逐项记下用户的每次操作，与第 3 节表格对照，多出的任何一步都登记为缺陷；用一个小任务书走通「任务书合并 → 派发 → CI → 自动评审 → 合并路由」。
