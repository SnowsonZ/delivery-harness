# 可观测性与审计设计（B46，v0.2）

状态：**已审定（用户 2026-09-29）**，可按第 6 节分期实现。来源：路线文档第 4 节的设计要点，结合 v0.1 代码现状展开；草案 1 只按「出事排查」设计，用户 2026-09-29 指出正常推进的工作同样要记录、可审计、能看到每个环节的输入与输出，本稿据此重排。与路线要点不同处在第 3 节标明。收 B36、B38、B40。

## 1. 要回答的问题

对任何一个已合并（或被拦下）的变更，事后能在一处复原：

1. **经过了哪些环节**，每个环节的**输入是什么、输出是什么、谁（哪个角色、哪个模型）做了什么决定、依据什么规则**。
2. **有没有环节缺失**：例如 R2 以上没有独立评审、自动合并没有路由判定、任务 PR 没有运行记录。缺失本身是审计发现。
3. **记录有没有被改过**：能发现事后的篡改（不能阻止，见 2.5）。
4. 出问题时：卡在哪一步、花了多久、守卫拒绝了什么。

**不做**：常驻守护进程（已定）；接入 Agent-Notification 收件箱（已定）；OTLP 导出（字段按 OTel 命名，留口子）；用事件做任何放行或拦截判定（见 2.5）。

## 2. 事件模型

### 2.1 交付环节与各自的输入输出

事件按这条链路组织。「落点」是今天这份信息在哪里（多数只在 job summary 或本机，过期即无）。

| 环节 | 输入 | 输出 | 决定与决定者 | 今天的落点 |
|---|---|---|---|---|
| 任务书 | 需求（设计方与用户对话） | 任务书（类别、预算、验收编号） | 用户批准合并 | git、PR |
| 派发准入与认领 | 任务书 sha、origin/main 提交 | 分支、槽位、守卫导出版本 | `taskbook` 准入规则 | 仅本机 |
| 执行（每轮） | 提示词 sha、槽位起点提交 | 提交范围、用量、守卫放行/拒绝计数、退出原因 | 守卫（规则名） | 运行记录（摘要）、本机事件流 |
| 本地判定（每轮） | 提交范围 | 每项检查结果、失败签名 | `verify` | 仅本机日志 |
| 推送与开 PR | 运行记录、提示词 | PR 号、head 提交 | 派发 | 运行记录 |
| CI 判定 | PR head、base | 风险等级与判级依据、每项检查、修复证据、度量 | `risk`、`verify`、`evidence` | job summary |
| 路由 | 风险、类别、预算、规模、运行记录 | 每条规则的满足与否及理由、`auto_merge` | `policy`（main 上的规则） | job summary |
| 独立评审 | PR、材料包（任务书、diff、CI 摘要）sha | 结论、发现（按严重度）、评审方与模型 | 评审方 | PR 评论 |
| 批准与合并 | 路由结果、评审、CI | 批准者、合并提交、合并方式 | 用户，或 App（仅 R0/R1 自动合并） | GitHub |
| 合并后 | 合并提交 | 抽审议题、escape 登记、周报数据 | 抽样规则 | 议题、周报 |

设计方自己实现的变更没有派发环节，链路从 PR 开出起；这两类变更的审计视图相同，只是前半段不同。

### 2.2 存储与契约：SQLite

用标准库 `sqlite3`（引擎仍零依赖）。一个库文件，WAL 模式、`busy_timeout`，多进程（钩子、派发、`verify`、各 worktree）并发写入安全；`PRAGMA user_version` 管理表结构版本。**库只在本机，不入库、不上传**（用户 2026-09-29）：`harness.db` 位于 git 公共目录（`.git/` 内），不会被 git 跟踪；新增的库与产物文件不落在工作区，无需改 `hygiene` 规则。放弃 JSONL 的理由：要按 trace、阶段、状态、引用哈希做关联查询（`trace`、`audit`、周报、告警去重），SQLite 直接支持，JSONL 需要每次全量扫描。

四张表：

| 表 | 内容 |
|---|---|
| `events` | 一行一个事件：`id`、`ts`、`trace_id`、`seq`、`prev_hash`、`hash`、`stage`、`step`、`status`、`duration_ms`、`actor_role`、`actor_host`、`model`、`decision_by`、`decision_rule`、`decision_reason`、`error_kind`、`error_signature`、`outputs`（JSON，扁平）、`engine_version`、`redacted` |
| `refs` | 事件的输入与输出引用：`event_id`、`direction`（in / out）、`kind`、`ref`（`path@提交`、URL 或 ID）、`sha256`、`size` |
| `artifacts` | 本机产物索引：`sha256`、`size`、`path`、`created`（内容在 `artifacts/<sha256>` 文件，不进库） |
| `anchors` | 链头锚点：`trace_id`、`stage`、`head_hash`、`fixed_in`（运行记录 / CI artifact / PR 评论）、`ts` |

事件示例（`events` 一行加它的 `refs`，此处按 JSON 表示；`events --json` 导出的就是这个形状）：

```json
{"ts":"2026-09-30T02:11:04.512Z","trace_id":"task/T005-x","seq":14,"prev_hash":"9f3c…","hash":"c07e…",
 "stage":"route","step":"budget","status":"ok","duration_ms":310,
 "inputs":[{"kind":"policy","ref":"main@a1b2c3d","sha256":"…"},{"kind":"class","ref":"K3"}],
 "outputs":{"ok":true,"window":10,"escapes":0},
 "decision":{"by":"policy","rule":"预算","reason":"窗口 10 次合并内逃逸 0 个，上限 1"},
 "actor":{"role":"engine","host":"ci"},"engine_version":"0.2.0"}
```

`hash` = 该事件规范化内容与 `prev_hash` 的 sha256（哈希链，见 2.5）。键名用 OTel 风格（`gen_ai.request.model`、`gen_ai.usage.input_tokens`、`harness.risk` 等）。`decision` 在有判定的事件上必填；`inputs` 是引用而非内容（2.4）。

### 2.3 追踪 ID

`trace_id` 取**分支名**（如 `task/T005-x`）；尝试序号、head 提交放 `inputs`。主分支上的事件用 `main@<短提交>`。

与路线要点的区别：要点写「dispatch 生成，写进 PR 正文，CI、review、policy 读回」。改为分支名的理由：

- 分支名是本机钩子、dispatch、CI 的 `head_branch`、review 的 `headRefName`、policy 五处天然共有的键，不需要任何一处读回另一处写的东西。
- PR 正文 Agent 可写，靠它传递 ID 既脆弱又不可信；设计方自己开的 PR 也自然有 ID。
- 代价：分支删除后同名重建会并入同一条时间线，靠 `attempt` 与 `ts` 区分。

### 2.4 输入输出如何记录：引用，而不是内容

审计要能核对「当时的输入输出是什么」，但事件本身只存元数据。做法是**内容寻址的引用**：

- **已在 git 或 GitHub 里的**（任务书、提示词、运行记录、diff、评审评论、PR 元数据）：引用 `path@提交` 或 URL 加 `sha256`，审计时重新取回并比对哈希。
- **只在本机的**（执行方完整事件流、verify 完整日志）：本机 `artifacts/<sha256>` 保存，事件里只有哈希与大小；默认不上传、不入库。
- **CI 产生的**（每项检查的输出、路由理由）：随 CI 事件 artifact 保存，同样只在事件里放哈希。

因此隐私规则不变（事件只放 ID、哈希、计数、枚举、时长）：`emit()` 写入前强制过滤，值只允许数字、布尔、≤ 120 字符字符串（`decision.reason` ≤ 200），拒绝形似本机路径（`/Users/`、`/home/`、`C:\`）与含换行的值，被丢的键计数写入 `redacted`。命令全文、会话正文、diff 内容不进事件。

**守卫放行**：每次工具调用都会经过守卫，逐条记放行事件量大。做法：**拒绝逐条记；放行只计数**——执行环节的输出里带本轮「放行 N、拒绝 M」，完整调用流由执行方事件流（有哈希引用）保存。设计方在本机的调用只记拒绝。

### 2.5 事件的可信度：防篡改，不防止

执行方与你是同一个 OS 用户，本机事件文件执行方能改能删；这是 B31（凭据隔离）的范围，v0.2 不解决。所以两条原则：

1. **事件不进任何判定**：放行、拦截、路由都不读事件。测试保证：事件开启、关闭、写入失败三种下，所有判定结果逐字相同。
2. **篡改可发现**：
   - 同一来源同一 trace 内的事件用 `prev_hash`/`hash` 串成哈希链，中间删改会断链。SQLite 不是只追加存储，同用户可以直接改库；链与锚点才是检测手段（可另加禁止 UPDATE/DELETE 的触发器防误操作，但对有意篡改无效）。
   - **锚点**：每个环节结束时把当前链头哈希写进**被评审或 CI 固定下来的地方**——运行记录（入库，经 PR 由用户批准）、CI 事件 artifact、PR 上的锚点评论。审计时本机链头与锚点比对，不一致即报告。
   - CI 侧事件由 main 上的工作流产生，可信度高于本机事件，审计报告分开标注来源。

诚实的限度：同用户的执行方在事后同时改本机事件与尚未固定的锚点，是无法发现的；锚点越早固定，窗口越小（每个环节结束即固定）。

## 3. 能记录的环节与内容

`emit()` 只包住**已有的结构化结果**，不改判定逻辑（新增 `engine/core/events.py`，标准库）。写入失败一律吞掉并向 stderr 提示一次，永不影响退出码；`HARNESS_EVENTS=off` 关闭。

来源列：**CI** = main 上的工作流产生，可信度较高；**本机** = 可被同用户改动（2.5）；**GitHub** = 从 GitHub API 取回的事实，事件里存引用。

### 3.1 设计与任务书

| 步骤 | 输入引用 | 输出与记录内容 | 来源 |
|---|---|---|---|
| `taskbook.admit` | 任务书 `path@提交` + sha256 | 通过与否；问题列表的规则名与计数 | 本机 / CI |
| 任务书合并 | 任务书 PR | 批准者、合并提交（走 `merge` 事件） | GitHub |

**记不了**：需求对话、设计方的推理与取舍。它们在 Agent 会话里，不在 harness 可见范围；可追溯到的是任务书的内容（git）与其批准。

### 3.2 派发（`dispatch`）

| 步骤 | 输入引用 | 输出与记录内容 | 来源 |
|---|---|---|---|
| `admit` | 任务书 sha、origin/main 提交 | 通过与否、任务编号、类别、预算（时长、重试、CI 轮次） | 本机 |
| `claim` | 分支名 | 认领成功/已被认领（远端分支存在） | 本机 |
| `slot` | origin/main 提交 | 槽位序号、起点提交 | 本机 |
| `guard_preflight` | 守卫导出的提交（`guard_ref`） | 必拒载荷是否被拒 | 本机 |
| `executor_round`（每轮） | 提示词 sha256、起点提交 | 执行方与版本、模型、时长、退出原因（ok / timeout / stall / stopped / error）、token 输入输出、费用、**守卫放行数与拒绝数**、完整事件流的哈希（本机产物） | 本机 |
| `local_verify`（每轮） | 本轮提交范围 | 每项检查结果（走 3.3）、失败签名、是否打转 | 本机 |

| 步骤 | 记录内容 | 来源 |
|---|---|---|

### 3.7 记不了的

- 需求与设计推理、执行方的思考与会话内容（隐私，且不可得）。
- 设计方在本机的守卫放行与命令内容。
- GitHub 平台设置的变更（ruleset、secrets、协作者）：在 GitHub 的审计日志里，harness 看不到；`verify` 检查平台设置是否齐全属 B45。
- 执行方在槽位之外做的操作（同一 OS 用户，B31）。

运行记录（`docs/runs/`，入库）保留为持久摘要，增加：`trace_id`、各环节链头哈希（锚点）、`stages` 时间线、`missing_context`。`run-check` 增加内容检查（B38）：记录里出现命令全文、本机路径、会话正文即失败。

## 4. 存放、留存与查询

| 层 | 位置 | 内容 | 留存 |
|---|---|---|---|
| 本机库（唯一的查询与审计数据源） | `<git 公共目录>/harness/harness.db`（SQLite，仅本机）、`…/artifacts/<sha256>` | 本机事件、引用、锚点与产物，以及**从 CI artifact 导入的 CI 事件** | 默认不清理（只有元数据，体量小；本机产物按 `[events] artifact_days` 清理，默认 30 天，B40）；没有守护进程，清理顺带在每天第一次 `emit()` 时做 |
| CI 运行层 | artifact `harness-events`（该次运行的事件导出，JSON 文本，含每项检查输出的哈希；CI 上的临时库不上传） | CI 环节的事件 | GitHub artifact 保留期（设为 90 天） |
| **审计账本** | 见 4.1 | 每个已合并 PR 一条**合并账本**：各环节的输入输出引用、决定、决定者、链头与锚点 | **长期**（与 git 历史同寿命） |

### 4.1 审计账本（需你选）

库只在本机，换机器或磁盘损坏就丢了；CI artifact 只有 90 天。要在这台机器之外保留可审计的长期记录，需要合并（或关闭）时把该 PR 的全部环节压成一条账本（**JSON 文本**，几 KB，只有引用与哈希；不把二进制库放进 git，文本可 diff、可审）。存放三选一：

- **A. 专用分支 `harness-audit`**：工作流用 `GITHUB_TOKEN` 追加一个文件 `<年>/<PR 号>.json`；对该分支加 ruleset（禁删除、禁强推，即只追加）。与 main 的「仅经 PR」规则不冲突（该分支不受它约束）。审计可用 `git log` 追溯，自带哈希链。**推荐。**
- **B. PR 上的一条机器评论**：随 PR 长期存在，无需新分支；但只有评论，检索与批量核对不便，评论可被有权限者编辑。
- **C. 提交进 main 的 `docs/audit/`**：最直接，但每个 PR 都要额外一个提交与 PR，破坏「一个任务一个 PR」，不推荐。

**前提**：账本要离开本机，这与「库只在本机」不冲突（账本是引用与哈希的摘要，不是库），但它是你需要认可的一次「外发」。若你不要任何账本外发，则审计的长期副本只有本机库，机器丢失即丢；此时 4.1 取消，`audit` 仍可对本机库工作。无论选哪个，PR 上都留一条简短的锚点评论（含账本引用与链头哈希），便于从 PR 找到账本。

### 4.2 查询与审计

```
bin/harness trace <任务编号 | PR 号 | 分支> [--ci] [--json]   环节时间线：输入 → 输出 → 决定；标出耗时最长与首个失败（`--ci` 下载 CI 的事件导出并导入本机库（幂等，按事件哈希去重））
bin/harness events [--since 1d] [--stage guard] [--status deny] [--json]  过滤、计数与导出
bin/harness audit <PR 号> [--all-merged --since 30d]            审计报告
```

`audit` 做三件事：

1. **复原**：按环节列出输入输出与决定，逐个引用重新取回并核对哈希。
2. **完整性**：按该 PR 的风险与类别检查应有的环节是否都在（R2 以上有独立评审、自动合并有路由事件、任务 PR 有运行记录与链头锚点、R0/R1 自动合并的批准者是 App）。缺失即发现。
3. **防篡改**：本机链头与锚点比对，账本与运行层比对；来源分开标注（本机 / CI / GitHub）。

周报：v0.2 首版不动数据来源；事件稳定后再加事件汇总（阶段耗时、守卫拒绝、升级原因、审计发现数）。

已知盲区：设计方在本机的守卫拒绝只在本机，不进账本；这是 2.5 的自然后果，不为此引入上传通道。

## 5. 告警

不引入常驻进程，也不新增渠道：告警就是在 PR（无 PR 时在议题）上评论并贴 `escalation` 标签，靠 GitHub 通知送达（已定）。在 `harness` job 末尾与 `auto-merge` 判定后 `if: always()` 运行 `bin/harness alert`；同一 trace 同一原因只评论一次（评论带标记，重复运行更新而不新增）。

| 触发 | 现状 |
|---|---|
| 完整性检查失败 | 只在 CI 日志 |
| 评审结论不通过，或评审方自身失败 | 有评论，无标签 |
| 派发卡死、超预算、打转 | 已升级，补 `trace_id` 与时间线链接 |
| CI 轮次只剩最后一轮 | 无 |
| 槽位内守卫拒绝数突增（阈值在 `rules.toml`） | 只记数 |
| 路由因误差预算耗尽拒绝自动合并 | 只在 job summary |
| **审计发现**：环节缺失或链头与锚点不一致 | 新增 |
