# 0002 在 harness 上做减法：核心档加平台适配层，停放派发与可观测性

状态：已采纳（2026-10-23，用户决定）。部分取代 0001 第 4 条。

## 背景

引擎建成一个月、800 多条提交，只装在 agent 工具类仓库里，没有产品仓库在用；接入工具 `adopt`（B45）仍未做。0001 把第二个项目的接入排在可观测性与 `adopt` 之后，结果可观测性（`engine/reports/` 约 3.7k 行）先于第二个使用方建成，接入一直没有发生。

用户最想解决的是审阅负担、结构腐化和跨会话失忆，三者都靠判定器与护栏解决，不靠派发和可观测性。限制采用的是重量和接入成本，不是能力。

## 决定

1. **核心档**：护栏（agent 层 5 个宿主 + git 层）、verify、卫生、风险判级、质量棘轮、文档检查、完整性、base 版本测试。它是 `adopt` 的第 1 档，安装不要求任何 GitHub 平台设置。
2. **可选档**（默认关闭）：任务书准入、验收映射、修复证据、事故回放、变异测试、R1 加强判定、发版核对。
3. **停放**：`engine/agents/`（派发、完整评审）、`engine/reports/`（事件、trace、审计、账本、告警、周报）与自治试验 B81。代码保留，安装不要求，不再投入，直到核心档在一个产品仓库用上。核心档只从中抽出两样：调用评审方做风险评级的一小段（评级只能调高，评审方与执行方不同家），以及精简证据包。
4. **平台适配层**：平台差异收进适配器，先做本地（无远程）与 GitHub，其他平台等真有仓库需要时再做。
5. **首轮新增机制只有三个**：待审队列（WIP 上限与每日摘要）、依赖方向规则、文档中代码路径锚点的检查。

## 理由与放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 新开一个精简仓库 | 重做已验证的护栏与判定器，形成第二套系统 |
| 先做完可观测性与 `adopt` 再接入（0001 第 4 条） | 一个月没有发生接入；没有使用方，可观测性的价值无从验证 |
| 整套照装 | 平台设置与任务书准入是用户确认最碍事的部分，正是接入的阻力 |

## 影响

- 冻结在途分支 `codex/observability-parallel-plan`、`codex/release-readiness-plan`、`task/302-trace-events-cli`；`docs/migrate-harness-design-docs` 搁置，待验收。
- `core/alerts.py` 对 agents 的延迟导入是 core 反向依赖 agents 的唯一一处，随 alerts 归入停放部分；`routing/` 里的 gh 调用移进 GitHub 适配器。
