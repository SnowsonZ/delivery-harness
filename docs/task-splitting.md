# 任务拆分流程

适用：一份已审定的设计要拆成多个派发任务（任务书 `docs/plans/task-*.md`）时。来源：用户 2026-09-29 在可观测性（B46）拆分中提出的要求；拆分的完整性与正确性以「最终功能完整、正确」为目标，不以「任务数量」为目标。

## 流程

1. **设计审定**：设计文档经用户审定（已定决定写在文中）。
2. **先跑通第一个任务**：只写并派发一个任务（冒烟任务，或依赖最少的首个任务），走通全链：派发 → 本地判定 → 开 PR → CI 等待 → 独立评审 → 合并路由。全链中暴露的流程与引擎问题先登记待办、修复，再继续；首个任务未成功前不拆其余任务。
3. **首个任务成功后，一次性拆完其余任务**：写全部任务书，并写**追溯表**（见下）。首个任务暴露的问题（白名单、验收写法、预算、执行方越界方式）折进后续任务书。
4. **拆分评审**：由不是设计方的 agent（Codex、OpenCode 等）只读评审，见下。
5. **处理评审发现**：设计方逐条处理，不采纳的写理由；用户看到评审结论与处理结果。
6. **一并提交**：全部任务书与追溯表作为一个文档 PR 提交（按期分拆需用户同意），由用户审。
7. **按依赖序派发**：合并后才派发（准入要求任务书已在 `origin/main`）。

## 追溯表

设计文档的每一条需求为行，写明：承担它的任务、验收断言（命令或测试名）、负责方（派发任务 / 设计方 / 用户）。规则：

- 正向：设计里每一项数据、事件、命令、配置、文档、迁移、告警、非目标都有归属，没有任务的行不能提交。
- 反向：每个任务至少对应一条设计需求，对不上的任务要么删要么补设计。
- 非代码工作也要有归属：本仓库自己工作流与内置副本的同步、平台设置（用户）、等价验证、版本号（用户）、文档与迁移条目。
- 跨任务的共用接口（存储 API、表结构、配置键、命令注册）明确由哪个任务定义、哪些任务依赖。
- 端到端验收有任务：单元测试覆盖不了「全链走通、人为制造缺陷能被发现」。

## 拆分评审检查项

评审方对照设计文档、追溯表与全部任务书，逐项检查：

- **完整性**：追溯表正反向无缺口；设计各节的验收标准都有可执行的断言。
- **正确性**：依赖顺序无环；同一文件的任务串行；白名单不含执行方不能编辑的文件（`.github/`、`.harness/`、已有测试、`implementer_protected`）；类别、风险、架构级声明与准入检查一致。
- **可验证**：每条验收断言在未实现时会失败（能说出怎么失败），不是恒真；验收命令在任务书写明的环境里可执行。
- **可完成**：每个任务在预算内能由一个 PR 完成；任务之间的接口签名一致。
- **一致性**：任务书里的接口、字段名、枚举与设计文档一致。

评审方输出：发现列表（严重度：阻断 / 严重 / 一般 / 建议；位置；理由；建议），末尾给出「可提交 / 需修订」结论。手工执行示例（只读）：

```sh
codex exec -s read-only -C <仓库> "<评审提示：附上述检查项与文件清单>"
```

工具化（`bin/dispatch review-plan`，复用独立评审的材料包与提示词机制）见待办 B54。
