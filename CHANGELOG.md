# Changelog

This project follows [Semantic Versioning](https://semver.org/). Versions are tagged by the maintainer.

## Unreleased — 0.1.0

First release as a standalone engine, extracted from [Agent-Notification](https://github.com/SnowsonZ/Agent-Notification) with its history (`git subtree split`).

- Package layout `engine/{core,guards,checks,routing,agents,reports,lang,prompts}` with a single entry point `engine/cli.py`.
- Vendored installation: `install` / `upgrade` write `.harness/engine/` and `.harness/engine.lock`; the new `integrity` check fails `verify` when engine files differ from the lock.
- Project settings moved to `.harness/config/` (`rules.toml`, `autonomy.toml`, new `checks.toml`), ratchet state to `.harness/state/`, incident replays to `.harness/project/replay_cases.py`.
- No user-specific defaults: agent identity, runtime interpreter, preserved paths, source directories, UI paths, release version file, verify checks, mutation targets, replay suites, reviewer models and report bots are configuration. Missing required settings are explicit errors.
- Language plugins (`engine/lang/`): Python and Swift signature comparison, dependency detection, function size and nesting.
- Templates for `bin/`, git hooks, agent-tool hooks and config skeletons (`templates/`); installation never overwrites existing files.
- CI templates for third parties: `harness`, `auto-merge` and `quality` workflows, two rulesets (two-account, single-account) and an `escape` issue template are installed under `.github/`. Project checks are read from `checks.toml`; the approval App's variable, secret and environment names and the approval mode are configured under the new `[platform]` section (`approval = "app" | "none"`); single-account mode is documented with its risks in SECURITY.md.
- `base-tests` no longer fails a project that has no `tests/` directory at the base commit.
- **Migration:** the delivery metrics and weekly report no longer print the built-in "v0.8.0 baseline" (it was the originating project's history). A project that wants a baseline line registers it under `[metrics.baseline]` (`label`, `values`) in `checks.toml`.
- `upgrade` refuses an engine checkout whose commit is not on `origin/main` (override: `--allow-dirty`) and prints the entries that start with `**Migration:**` of this changelog newer than the project's current lock; procedure in `docs/upgrading.md`.
- The CI workflows that decide "CI passed" and count CI rounds (`dispatch`, merge routing, delivery metrics, weekly report) are configurable (`rules.toml` `[dispatch] ci_workflows`, default `["harness"]`) instead of the hard-coded name `build`; dispatch waits for every listed workflow on the pushed commit.
- `dispatch` retries a failed `gh run list` query up to three times while waiting for CI, so a single network drop no longer aborts a dispatch.
- Template only: the `audit-ledger` job's `Publish merge ledger` step now exports the git author/committer identity via environment variables and runs `gh auth setup-git` before `ledger.py`. The ledger's temporary clone has neither the workspace's repo-level git config nor the checkout credentials, so on hosted runners the first real run failed with `Author identity unknown` (and the push would fail next, silently, under `continue-on-error`). Consumers pick this up on their next `upgrade`.
- Fixed `bin/dispatch review`: it imported the pre-restructure flat module name and failed with `ModuleNotFoundError` since 0.1.0 (`bin/harness review pr <n>` was unaffected).
- **Migration:** a project whose CI workflow is not named `harness` (for example one that still uses `build`) must set `[dispatch] ci_workflows` in `.harness/config/rules.toml`, otherwise dispatch waits for a workflow that does not exist.
- Migration aid: when `origin/main` still has the flat `harness/` layout, the git guard and dispatch read rules and export guards from the old location. Remove once all consumers have migrated.

- **Event log (observability, phase 1).** Gates, dispatch, guards and routing write structured events to a local per-repository log: `harness/harness.db` in the git common directory (SQLite in WAL mode, shared across worktrees, inside `.git` and therefore untracked) plus content-addressed artifacts under `harness/artifacts/<sha256>`. Stages in this phase: `guard`, `verify`, `dispatch`, `ci`, `route`, `review`; an event carries source, trace id, stage/step/status, decision metadata and privacy-filtered inputs/outputs (local paths and long strings are dropped, command full text is never recorded).
- Events are advisory by construction: a failing event sink never changes judgments, exit codes or output (one fixed stderr notice per process), the guard logs denials only (allow stays silent), and `verify`/integrity summaries are additional rows, not new verdicts.
- **Tamper-evident chain.** Events are chained per `(source, trace id)` with `seq` + `prev_hash` + canonical SHA-256; `verify_chain` reports gaps or edits instead of guessing; content-addressed artifacts are written atomically (temp file + atomic replace, deduplicated by hash) and a database written by a newer engine is reported as unverifiable rather than silently accepted.
- **Source isolation.** On real GitHub Actions the source is `ci:<run_id>:<run_attempt>:<job>` so concurrent jobs chain independently; other CI reads `ci`, local runs read `local`; `actor.host` still displays `ci`.
- Switched on by default; `HARNESS_EVENTS=off` (environment, takes precedence) or `[events] enabled = false` in `checks.toml` turns writing off. The optional key ships commented in the config template; this phase adds no required configuration.
- **Migration:** the event log adds an optional `[events]` section to `.harness/config/checks.toml` (`enabled`, on by default; the environment variable takes precedence). No action is needed to keep current behaviour; set the key only to turn the log off.

- Independent review materials now include the referenced task brief: when path-based detection misses but the PR title or description references `docs/plans/task-*.md`, the materials carry the full brief instead of a placeholder; detections that already match are unchanged.
- **Dispatch alerts (observability phase 2).** The last CI round within budget warns on the PR (or on the escalation issue when no PR exists) before the wait begins; guard denials above a configured per-round threshold warn with the denied-tool counts; each (trace, reason) alert maintains a single comment or issue, updated in place and never re-posted (escalations are separate comments and are not deduplicated); escalation bodies gain a trace/timeline section. Publishing failures never change judgments, exit codes or escalations.
- **Migration:** dispatch alerts add an optional `[alerts]` section to `.harness/config/rules.toml` (shipped commented in the template; deleting the section turns alerts off entirely). `guard_denials_threshold = <positive int>` enables the guard-denial warning; unset keeps current behaviour.
- New `review-plan` subcommand (`bin/harness review-plan <plan-doc>`): assembles a task-split review material pack (the plan doc plus every local doc it links: traceability, contracts, all task briefs; missing links are listed), runs the configured read-only reviewer over it and writes the verdict and material list to `build/review/plan-verdict.md`. Entry events are recorded in the `review` stage.
- `dispatch --resume` on a branch that already has an open PR now reuses its number instead of crashing on `gh pr create` (feedback for later CI rounds goes to the existing PR; when no PR exists the previous create path is unchanged).
- After an upgrade, the harness CI workflow uploads a `harness-events` artifact per run (JSON export of that run's events, retained 90 days) and appends an event summary to the job summary; uploads also happen after failed runs. Template-only in this change - a project's real workflow copies it at its next upgrade.
- After an upgrade, the harness workflow's observation job gains a "Sync GitHub facts" step (merges, spot-audit and escape facts synced into the local event log via the installed `github_events.py`); the job's GitHub permissions are raised to `pull-requests/issues: read`. `merge_method` heuristics distinguish merge commits; squash-vs-rebase disambiguation lands with the follow-up task noted in the plan.
- Independent review no longer truncates the review diff at 200,000 characters: the full `git diff` is written to `build/review/diff.patch`, and diffs over 2 MB are sharded on file boundaries into `diff-01.patch`, `diff-02.patch`, … (each shard within 2 MB, shards concatenate to the byte-identical full diff; a single file above the limit gets its own shard). The evidence pack lists every diff file with its line count at the top of `pack.md` and declares the shard count when sharded; the reviewer prompt and the C6 audit materials read the same shard set. No configuration keys.
- Run records shrink to an attempt-scoped index: `stages` now covers only the current attempt (earlier attempts leave a `status: "prior"` pointer row for push/CI steps) with seven scalar fields per entry - full detail stays in the event log (`bin/harness trace`); records self-normalize before commit (oversize `stages` truncated and flagged, CI runner paths masked) so the hygiene guard no longer kills dispatch at the record step; dispatch slots are returned on every exit path and stale slots (dead pid, unpushed work salvaged) are reclaimed automatically. Consumers parsing `stages` keep working: old twelve-field records validate unchanged, the new shape is accepted by the run-record content check.
- New `audit` subcommand (`bin/harness audit <PR>`): reconstructs the safety-critical evidence of a merged PR and re-verifies every reference against its recorded hash. `audit --all-merged [--since <duration|UTC time>]` pages through every merged PR inside a deterministic time window; `--json` prints the full report (`{"window": …, "prs": […]}` in batch mode). Exit codes: 0 when every applicable reference verified, 1 when there are findings, 2 for bad arguments, an overall API failure or a PR that cannot be audited. Git files are fetched at `path@rev` and compared by original bytes (trailing-newline changes are detected), immutable comment bodies byte-for-byte, mutable PR fields by re-rendering with the same recipe as the review snapshot (drift reported as `snapshot_changed`, not byte tampering), local artifacts by hash/size with retention expiry distinguished from missing files, and CI event packages through the shared hash-verified import. Reference content is only parsed and compared, never executed; finding reasons never echo reference content; paths cannot escape the repository.
- Each audit run also writes observation events for the weekly report: one `ci/audit.summary` per run (per PR in batch mode, including PRs that cannot be audited) plus one `ci/audit.finding` per finding, with outputs restricted to safe fields (PR, head SHA, rule/severity counts, flattened coverage; finding events additionally carry rule/severity/source/stage/ref for weekly dedup by PR and head). Finding reasons and other private content never enter events, and observation failures never change exit codes or output. No configuration keys and no migration.
- **Audit completeness and tamper-evidence findings.** Beyond re-verifying references, `audit` now checks that the stages a change required actually happened: R2+ has an independent review whose reviewer is neither the designer nor an implementer; an auto-merge has a `route.result` with `auto_merge=true` from a trusted CI chain; a task PR (declared class, implementers in the review summary, or an existing run record - any of the three) has a run record with fixed stage anchors, while designer PRs are exempt from dispatch records; in `app` mode an R0/R1 auto-merge is approved by the App and bound to the merged head, and `none` mode never demands an approval. It also verifies each `(source, trace)` hash chain, checks every fixed anchor (run record / CI artifact / PR comment) against the corresponding chain prefix instead of the final head (legitimate later appends do not false-positive; tail deletions are caught even when the internal chain stays valid), and compares ledger chain heads with the run layer. An unreadable event database is reported honestly instead of being treated as "no events". New stable rules: `missing_review`, `missing_route`, `missing_run_record`, `missing_anchor`, `reviewer_not_independent`, `approval_actor`, `approval_head`, `chain_invalid`, `anchor_mismatch`, `ledger_mismatch`, `configuration_error`.
- Optional `[audit]` section in `checks.toml`: `require_review_risk` (0..3, default 2), `require_route_for_auto`, `require_run_record_for_task` and `verify_anchors` (booleans, default true). Defaults follow the design rules; unknown keys, wrong types or out-of-range values produce a `configuration_error` finding and exit code 2 instead of being silently relaxed, and the section only shapes the audit report - policy/guard/verify verdicts never read it. No migration (unset keys keep the default behaviour).
- **Alert command and workflow alert steps (observability phase 4).** New `alert` subcommand (`bin/harness alert <reason> [--pr <n>] [--trace <branch>] [--task <id>] [--bundle <dir|file>] [--json]`): publishes one deduplicated alert per (trace, reason) through the shared C4 API - a PR comment or, with no PR, a reused escalation-labelled issue. Remote markers are the only dedup authority: deleting the local event log (or running on another machine) still updates the same remote comment. `--bundle` reads a `harness-events` package (data only, never imported or executed) and publishes only when it contains the reason's trigger evidence (`verify`/integrity failure, route budget rejection, audit completeness findings); unknown failures trigger nothing. All seven trigger families of the observability design have stable reason keys: `integrity_failure`; `review_rejected`/`review_error`; `dispatch_stall`/`dispatch_timeout`/`dispatch_loop`/`dispatch_budget`; `ci_last_round`; `guard_denials`; `budget_exhausted`; `audit_missing_stage`/`audit_anchor_mismatch`. Independent review now adds the escalation label and publishes/updates its alert after the review comment is posted (rejected verdicts and reviewer failures; review is never re-run), and an alert API failure never changes the review, verify or routing conclusions. Carrier split (F3): the harness workflow calls alert only at the end of push-to-main runs (integrity of the merged engine copy; `issues: write` only), while every `pull_request`-triggered job keeps read-only token permissions for same-repo and fork PRs alike; PR success and failure are carried by a separate `alert` job in the auto-merge workflow that runs after the judge with `if: always()` (a success-only gate no longer misses failed CI), executes default-branch engine code only, treats the evaluated head and event packages as data, and holds the minimal `issues`/`pull-requests: write` plus `actions`/`contents: read`. Template-only change: a project's real workflow copies update at its next upgrade.
- **Contract route for R2 implementation PRs.** `policy` can auto-merge an R2 PR whose every changed path is under `[contract_route] allowed` (in `autonomy.toml`), whose task brief is already on the default branch (not added by the PR itself), whose run record passes `run_check`, whose machine class is L4 within its error budget, and which carries both an independent-review marker (verdict pass, no serious findings) and a designer sign-off marker (verdict pass, at least one targeted mutation, all caught) bound to a head with identical content. Markers are trusted only from `[identity] agent_login`, must appear exactly once on their own line, and a reviewer from the same model family as the implementer is accepted only when the review audit records the model as reported or explicitly requested. While only the markers are missing the judge reports `pending` and the auto-merge workflow labels the PR without requesting owner review. Without a `[contract_route]` section (the template ships it commented out) no PR takes this path.
- New `bin/dispatch signoff <PR>` posts the designer sign-off marker; when both markers are present it re-runs only the `pull_request`-triggered harness run so the judge sees them. The auto-merge workflow's `merge-app` job syncs a branch that is behind the default branch (compare `behind_by`, not `mergeStateStatus`, which reads BLOCKED before approval) and labels conflicting branches `escalation` instead of approving; conflicts take precedence over syncing.
- Optional `review_after_ci` in `rules.toml [dispatch]` (default false): once CI passes, the dispatch process runs the independent review itself. `[review] chain` (default `[reviewer]`) lists reviewers to try in order; a reviewer that fails (quota, missing binary) or is the designer is skipped.
- The agent-layer guard denies the implementer role from posting PR comments or reviews and from running `review`/`signoff`, including via `bin/harness`, `cli.py`, `python -m engine.cli` with any interpreter options and `gh -R`/`--repo` spellings; the run-record check accepts these denials as legitimate.
- The merge ledger and `audit` accept review evidence bound to an earlier head whose content is byte-identical to the merged one; the `audit-ledger` job checks out full history (`fetch-depth: 0`).
- Independent reviews on the shared review workspace are serialized by a kernel file lock (`<workspace>.review.lock`, `flock` plus inode check) across `review pr`, both calibrations and `review-plan`; Codex reviews run with sub-agents disabled (`-c agents.enabled=false`).
- Taskbook admission events no longer scale with the number of task briefs (B94): `ci/taskbook.admit` is emitted only for failing briefs (fields unchanged), plus one `ci/taskbook.summary` per run with the `total`/`failed` counts and the admission decision; passing briefs no longer emit per-file events.
- **Migration:** `.harness/config/rules.toml [risk] contracts` should include `docs/specs/**`, as the template does (spec changes are contracts and need owner review); add it if your copy predates this release.
- **Migration:** re-copy `.github/workflows/auto-merge.yml` and `harness.yml` from `templates/` after upgrading; `upgrade` does not touch `.github/`. The approval App needs only *Pull requests: read and write*; branch sync uses a separate sync App (see the sync App entry below).
- CI events written by harness runs are now actually importable (B116): `trace <PR>`, `trace --ci` and the merge ledger read them again. The `gh pr view` queries no longer use the non-existent `baseRepository` field (the repository is parsed from the PR `url`, enterprise hosts included), `load_ci` matches workflow runs by the REST field name `head_sha` instead of the `gh run list` spelling, and event packages exported by `pull_request` runs record the PR's head SHA taken from the event payload instead of GitHub's synthetic merge commit (the loader verifies against the API, so every PR package used to be rejected as `origin_mismatch`). A new field-contract test walks every `--json` call site under `engine/` and validates each field against a gh 2.92.0 per-command snapshot (unresolvable call sites must be whitelisted with a reason).
- Already-exported CI event packages whose `origin.head_sha` is a synthetic merge commit remain unimportable; the fix applies only to runs exported after the upgrade.
- **Migration:** none.
- Branch sync and approval now use two separate GitHub Apps. The approval App's token step only requests `pull-requests: write`; a new sync App (repository variable `HARNESS_SYNC_APP_CLIENT_ID`, secret `HARNESS_SYNC_APP_PRIVATE_KEY` in the same environment, both configurable under `[platform]`) updates a behind branch with `gh pr update-branch`. The ruleset requires the last push to be approved by someone other than the pusher, so when one App both synced the branch and approved it, its approval no longer satisfied that rule and `gh pr merge` was rejected — any PR that had been synced could never auto-merge. A behind PR with no sync App configured is no longer synced with the approval App's token: the workflow comments on the PR asking for a manual sync and the job succeeds without approving or merging.
- **Migration:** configure a second GitHub App for branch sync (*Contents: read and write*, *Pull requests: read and write*; variable `HARNESS_SYNC_APP_CLIENT_ID`, secret `HARNESS_SYNC_APP_PRIVATE_KEY` in the `harness-auto-merge` environment — see README "Platform setup"). Without it, behind PRs get a comment asking for a manual sync instead of being synced. Re-copy `.github/workflows/auto-merge.yml` from `templates/`; the approval App no longer needs *Contents: write*.
- `verify` in the `default` or `full` tier that passes with a clean worktree writes a pass record `harness/verify-pass/<HEAD tree>.json` (git common directory, carrying the `tree` of `.harness/engine.lock`). The verified HEAD tree and engine identity are fixed before the checks start and re-read before writing: if either changed during verification, or tracked files are no longer clean, no record is written, so an old verification result can never be bound to a new tree. `pre-push` then skips re-running verify when every pushed local commit's tree has such a record, the worktree has no tracked changes and the record's `engine_tree` equals the current lock; any read/write error counts as "no record" and verify runs as before, and protected-branch, force-push and hygiene denials still apply first. Only pre-push reads the record — the `verify` command itself, dispatch re-verification and CI always run in full. Accepted risk (also documented in the code): the record lives on the local machine, so an executor could forge it to make pre-push skip verification; the consequence is limited to bad code being pushed, which dispatch re-verification and CI (neither reads the record) still catch.
- **Migration:** optional `grow_only_cases` key in `rules.toml [risk]` - no action needed: the key is off unless you add it, existing configs keep the previous grading. When enabled, a modified replay-case list whose only change is appending fully literal `Case(...)` entries to the end of `CASES` is graded R2 instead of R3 (`rule: grow_only_cases`), so a `Defect:` fix PR can take the contract route. The structural comparison parses both revisions' committed blob bytes with `ast.parse` only - PR content is never executed, and PEP 263 coding declarations are detected exactly the way Python itself does (`tokenize.detect_encoding`): the head's effective encoding must normalize to UTF-8 (`utf-8-sig` accepted) and any declaration line must match the base's byte-for-byte (none in either is the normal case) - and it requires every other top-level statement (`BASELINE`, `GUARDED`, `DEFERRED`, imports, the docstring) plus the `CASES` statement itself apart from the list (type, targets, annotation, `simple`) to be unchanged; anything else keeps the previous grading.
- **Native auto-merge (B102).** The auto-merge workflow no longer merges immediately when the harness finishes: merge-app approves the evaluated head and enables GitHub's native auto-merge (`gh pr merge --auto --merge --match-head-commit <head>`), so required checks that finish later, unknown merge states and test-merge commits are GitHub's problem. Immediately before enabling, merge-app re-runs the exact `policy` command the judge ran (workflow token only; the job gains `actions: read` because the re-check reads CI rounds) and, on rejection, revokes a stale auto-merge request and skips approval and enabling. The enabling token is the sync App's when configured, otherwise the workflow token (the approval App only approves); when enabling fails and no request exists, the workflow falls back to an immediate merge with the same token and comments once asking for the repository's "Allow auto-merge" setting. Spot-audit issues are registered idempotently before any merge command (native and fallback paths alike, `merge-app` and `merge-direct`), with per-PR `concurrency` groups serializing both jobs; a failed issue query fails the job (no merge this run). The workflow also triggers on `push` to the default branch: a `platform` job prints the `[platform]` config (new `automerge platform` subcommand) and a `sync-waiting` job (sync App token, serialized) updates waiting auto-merge PRs that fell behind and comments/labels `escalation`/disables auto-merge for conflicted ones (`mergeable` unknown is retried three times then skipped; forked, non-default-base and non-auto-merge PRs are never touched; without a sync App the job skips). The `alert` job now runs only for `workflow_run` events, and `request-review` disables a PR's auto-merge when the judge rejects. Engine side, every veto closes the request through the new `GitHub.disable_auto_merge` (never raises, prints on failure): a rejected review verdict or a "pass" with serious findings (criterion shared with `signals.review_status` via the new `review_marker_status`/`signoff_marker_status` pure functions), a failed designer sign-off, and the `budget-exceeded` label. The judge summary's audit hint now says the spot-audit issue is registered before merge. Template-only change: a project's real workflow copies update at its next upgrade.
 In `approval = "none"` mode the enabling and fallback both use the workflow token, and a workflow-token merge does not trigger the default branch's `push` workflows, so the `sync-waiting` chain is inactive there (see SECURITY.md "Single-account mode").
- **Migration:** turn on Settings → General → Pull Requests → **Allow auto-merge** in the repository — without it, enabling fails, the workflow falls back to an immediate merge and comments on the PR. Re-copy `.github/workflows/auto-merge.yml` from `templates/` (new `push` trigger, `platform`/`sync-waiting` jobs, merge-app re-check); the approval App still only needs *Pull requests: read and write*. Shutdown is now: disable the workflow (Actions → auto-merge), cancel or wait for in-flight runs, then run `python3 .harness/engine/cli.py automerge-off` until it exits 0 (`--dry-run` lists without changing) — it revokes every outstanding auto-merge request for shutdown and class recycling and exits 0 only after re-checking that no incomplete run and no request remain.
- CI round budgets no longer count sync merges (B104): a head whose commit is a sync merge (two or more parents, every parent after the first an ancestor of the evaluated base) is excluded from `branch_rounds`, which now takes the caller's `cwd` and the mainline; ordinary merges, merges with only some parents on the mainline, unknown commits and git errors still count, and reruns of the same head still count once. Accepted risk (also in the code comments): an executor can smuggle fixes into a sync-merge commit to undercount a round — the budget is a cost control, not a security boundary; the changes still appear in full in the diff and are reviewed and signed off as usual.
- The accepted residual race of the pre-enable re-check (a veto landing between the re-check and the enabling, seconds wide) is documented in SECURITY.md "Native auto-merge and its residual race"; closing it completely would require making contract eligibility a required status check, which would also block owner-initiated manual merges.
- `verify --push`: a light tier (quick checks + the quality ratchet + doc links, no full test run, about 2 seconds) that the pre-push hook can use instead of the default tier. Set `[guard] pre_push_tier = "push"` in `.harness/config/rules.toml` (read from `origin/main` like the other guard rules); the default stays `"default"` and an invalid value falls back to it. Meant for projects whose merge gate is a required CI check: pushes that only delete a branch or change docs no longer wait for the unit tests.
- **Migration:** optional `[guard] pre_push_tier` key in `rules.toml` (shipped commented in the template) - no action needed: without it the pre-push hook behaves as before. Projects with required CI checks that run the full tests can set it to `"push"`.
- CI `consumer-contract` now runs the consumer's full `bin/verify --full` after upgrading it with the engine under test (consumer-equivalence verification, formerly done by hand by the designer, becomes a CI fact the independent reviewer can read). The consumer's macOS-only checks (`requires = "macos"`, e.g. Swift) show as skipped on Linux.
- Independent review: the prompt no longer asks the reviewer to look for the designer's local mutation-run output (the designer's signoff marker carries it) and says consumer equivalence is read from the `consumer-contract` CI result; `docs/templates/review-checklist.md` follows. `build/review/ci.md` falls back to `statusCheckRollup` and states the reason when the CI result cannot be read, instead of the bare "cannot read".
- **Migration:** none for projects with their own CI. Projects whose review checklist copy still says "attach G2 evidence" should re-copy `docs/templates/review-checklist.md`.
- `audit` no longer reports `ledger_mismatch` for GitHub fact snapshots that the merge workflow and the auditing machine each recorded with their own timestamps; differing events are still reported, and a recorded merge snapshot with no matching merge fact on the auditing side is now reported too (a later label change, or a superseded audit-sample or escape snapshot, is not). **Migration:** none.
- The CI event loader now also imports the auto-merge judge runs' event packages (they are triggered by `workflow_run` and belong to the default branch in the API, so the per-branch query never found them): route results reach `trace <PR>`, the merge ledger and `audit` (no more `missing_route` for auto-merged PRs once the template below is in place). Judge runs are linked to their PR by the run name rendered by the workflow definition on the default branch - never by the package's own claims - and each judge package is still verified against that run's own API record; the runs listing is fetched per workflow without filter parameters and stops early based on the PR creation time, so the read volume does not grow with the repository's run history.
- **Migration:** after upgrading, re-copy `.github/workflows/auto-merge.yml` from `templates/` (it gains a top-level `run-name`; `upgrade` never touches `.github/`). Without the re-copy, judge runs' events keep failing to import exactly as before - no error is added.
- Task brief admission now checks the line headroom of every existing whitelisted Python file (`bin/dispatch run` and `bin/harness taskbook <path>`): a declared net addition that would cross the 800-line quality ratchet, or no declaration within 100 lines of it, is rejected before dispatch with a split/move hint; admission also emits a non-blocking hint when the acceptance table has 10 or more rows (T718/T719 both overran one dispatch budget on size). The check never runs in `check_all`, so historical briefs stay green in `verify`. **Migration:** none.
- Dispatch no longer destroys uncommitted work in a slot: before a slot worktree is removed, uncommitted changes (staged, unstaged, deleted and untracked files, honouring `.gitignore`) are backed up to `refs/backup/dispatch/<branch>/<UTC timestamp>` with restore instructions on stderr; a dispatch-record commit rejected by a git hook raises a clean stop (exit code 2, hook output tail included) instead of a traceback crash; and `--resume` merges the default branch into the task branch first (fast-forward when only behind, aborted merge plus stop on conflict), so a revised brief on main is picked up instead of a stale one. **Migration:** none.
- **Weekly report event summary (observability phase 5).** `weekly` appends one new section, "事件汇总（B46）", after the existing report text: the old sections, data sources and the hidden `weekly-data` comment are a verbatim prefix, so `history_from_comments` and `publish` keep working unchanged. Part A uses only repository-retrievable sources: per-stage durations from this week's merged PRs' ledgers on the `harness-audit` branch (`git show origin/harness-audit:<year>/<PR>.json`, events only - run-record summaries are not double-counted), plus run-record metrics (total `executor_seconds`, attempts and task counts kept separate, `exit`/`escalation` distributions, executor guard denials summed by rule text and labelled "rule hits" - a denied call can hit several rules; the designer side is reported as "not obtainable, local only", never 0; missing-context categories with abnormal or absent `missing_context_status` counted as under-coverage). Part B, the local event database, is a separate subsection that is never merged into A and is enabled by environment, not by database presence: `CI=true` always turns it off (a runner's temporary database is not local history) with "不可用（CI 环境不统计本机库）"; outside CI the module probes the database itself (read-only open, `PRAGMA user_version` - a missing, corrupt or newer-schema database and a legal empty one are distinct), and counts only `source=local` events in the UTC week window: local stage durations, escalate reasons, guard denials split by kind × role (the `git`/`engine` group is marked unattributable and never summed), denied tool calls (`executor_round` counts - a different unit from rule hits, listed separately with no cross-check), and audit findings per PR/head taking only the latest run (no stale findings, no accumulation across re-audits, updated heads listed separately; in CI and without a local database the audit count is "不可用", never 0). Anything unreadable is "不可用" with a reason; a value is 0 only when there is data and it is zero. No configuration keys.
